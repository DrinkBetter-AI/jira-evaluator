# Task 3B assumptions — the People page

One bullet per ambiguous call, what was chosen, and why.

## `render_shared.py` was not touched at all

- The task grants permission to edit `_render_scorecard` in
  `render_shared.py` and nothing else in that file, and says the within-role
  claim has to become true "one of the two must happen" (wire the cohort, or
  change the caption). It does not require touching `_render_scorecard`
  specifically - that function is the *Streamlit-native* single-person
  scorecard used by `_render_individual_page` (the drill-down every page
  reaches through `_one_person_instead`), and this task's brief is explicit
  that the People page's own scorecard is HTML through the kit
  (`theme_html.scorecard()`), built independently. Wiring the cohort inside
  `_render_scorecard` would have fixed a claim that function does not itself
  make (it has no "compares within your role" caption anywhere), while
  leaving `pages/people.py`'s own claim - the one this task is actually
  about - unwired unless duplicated there too. Wiring it once, directly in
  `pages/people.py` (`_components_for_person`, below), makes the page's own
  caption true without touching a shared file four other agents are editing
  concurrently. `render_shared.py` is unmodified by this task; `git diff
  render_shared.py` against the pre-3B tree is empty.

## The cohort wiring itself

- `_components_for_person` calls `kpi.components(..., peer_resolved_7=pool,
  include_gaps=True)` where `pool` is built from `roles.peer_cohort` - the
  person plus their actual cohort peers, `None` when the cohort is below
  `roles.MIN_PEERS` (3). `kpi.components` already refuses to score "Delivery
  vs team" below `kpi.MIN_PEERS` (also 3, a separate constant per
  `docs/assumptions/2C.md`) - passing `None` when the cohort itself is
  insufficient just means both gates agree.
- When the cohort is insufficient, `kpi.components(include_gaps=True)`
  still appends a placeholder "Delivery vs team" row via `kpi.gap_components`,
  but its note is the generic `kpi.COMPONENT_INPUTS` text ("needs the
  same-week resolved counts of at least 3 teammates") - true, but not the
  specific number the task asks for ("render the insufficient-peers state
  with the actual peer count"). `_components_for_person` overwrites that one
  placeholder's `.detail` and `.n` with `roles.peer_cohort(...).reason` and
  `.peer_count` after the fact, once, rather than reimplementing
  `kpi.components`'s component list from scratch. `kpi.Component` is a plain
  (non-frozen) dataclass, so this is an in-place field assignment, not a
  rebuild.
- Verified against the live default roster
  (`roles.load_roster()`, no env overrides): of the sixteen role keys, only
  the folded `frontend + frontend-mobile + mobile` cohort (David, Mohsen,
  Farid, Ali - 4 active people) clears `MIN_PEERS`. Every standalone role
  (platform: just Tam, backend: just Shawn, ai-recommendation: just Mehdi,
  ...) has zero cohort peers. This matches the task brief's own prediction
  ("most cohorts are insufficient, that is correct") and is asserted by
  `tests/test_people.py::test_a_role_with_fewer_than_min_peers_...` (Tam, 0
  peers) and `..._enough_peers_gets_a_real_cohort_percentile` (David, 3
  peers, a real percentile computed against three peers with different
  credited-resolution counts).
- The page's caption states the mechanism plainly ("Peer comparison uses
  each person's own role cohort ... a cohort under 3 peers shows its actual
  peer count instead of a percentile") rather than only asserting the
  within-role claim, so the caption and the code are the same sentence, not
  two things that have to be kept in sync by hand.

## Score consistency between the table and the scorecard

- The table's `score` column comes straight from `people_table.people_table`
  (2B's own cohort wiring inside `_score_for`/`_peer_pool`, already correct
  and out of this task's ownership). The scorecard's component breakdown is
  computed independently in `pages/people.py`, via the same public
  functions (`integrity.credited_resolutions`, `integrity.integrity_flags`,
  `kpi.components`/`overall`/`coverage`, `roles.peer_cohort`) on the same
  bulk frames (`open_tickets`, `gradable_tickets`, `prs`, `combined_events`,
  `resolved_tickets`) that were handed to `people_table.people_table`. This
  is not the same code path as 2B's private `_score_for`/`_credited_counts`
  (those are private to `people_table.py`, out of this task's file
  ownership, and the frozen 2B contract exposes only `people_table()` and
  `COLUMNS`) - it is a second, independent computation over the same public
  API and the same inputs, which is expected to agree with the table's
  number for the same person and does in every fixture this task's tests
  build. A true byte-for-byte guarantee would require 2B to expose its
  internal `Component` list, which is outside this task's frozen contract.

## Where the bulk frames for the table and scorecard come from

- `open_tickets` is `hygiene.estimate_policy(_metrics_df(bundle.df,
  include_backlogs=False), BACKLOG_STATUSES)` - the same
  filter-then-estimate-policy pipeline `_render_individual_page` already
  applies before calling `_render_scorecard` (`whole_board =
  _metrics_df(organization[owners == name], include_backlogs=False)`),
  generalized to the whole org rather than one person's slice.
  `people_table.py`'s own docstring says its `open_tickets` parameter must
  already carry `idle_days`/`carry_over_count`/`has_estimate` - this is
  where that happens; `carry_over_count` is already on `bundle.df` from the
  Jira fetch itself (`jira_client.py:873`), so only `estimate_policy` needed
  calling.
- `gradable_tickets` is `ticket_quality.score_tickets(bundle.df)` - the
  whole open board, unconditionally, mirroring the existing
  `_render_ticket_quality`/`_render_scorecard` pattern
  (`ticket_quality.score_tickets(gradable_source)` then filtered to
  non-null `quality_score`) but organization-wide rather than one person's
  `theirs` (owned + reported) slice, since `people_table.py` only ever
  slices this frame by `assignee`.
- `resolved_tickets` is `bundle.data.get("resolved_30")` - the one bulk
  resolved-ticket frame the engineering reads already fetch (`expand
  changelog`), same source `pages/delivery.py` uses for its own org-wide
  reopen/unattributed figures.
- `combined_events` (`bundle.events` plus `integrity.changelog_events(resolved_tickets)`,
  deduped on `(key, entry_id)`) is a direct duplicate of
  `pages/delivery.py`'s private `_combined_org_events`, not an import - that
  function is private to a page this task does not own, and the
  construction is four lines. Same documented blind spot travels with it: a
  ticket that fully resolved and closed more than 30 days ago is invisible
  to `credited_resolutions`/`integrity_flags` here, same as it already is
  on Delivery.

## Evidence rows are audit trails, not exact query replays

- "PRs merged this period" and "Reviews given" link to a GitHub code search
  (`github.com/search?q=org:<org> is:pr ...`) scoped by the person's GitHub
  login when the roster has one mapped, and by the bare query when it
  doesn't (a non-code role has no login - the link still resolves, it just
  isn't person-scoped). "Tickets resolved (changelog-credited)" and
  "Estimate revisions mid-flight" link to a Jira JQL search
  (`<site>/issues/?jql=...`) built from `assignee = "<person>"` plus a
  resolved-date or updated-date window - Jira's basic search UI has no way
  to query "an estimate field changed in the changelog" directly, so that
  last link is a reasonable starting point for a human to look, not a
  literal replay of `integrity.estimate_churn`'s own logic. The task's
  acceptance bar is "a resolvable URL", not "an exactly reproducing query";
  `tests/test_people.py::test_every_evidence_row_carries_a_resolvable_url`
  checks every row's URL starts with `https://`, not that Jira/GitHub would
  return the identical count.

## The 12-week sparkline is PR-merge count, not size-weighted points

- The mockup's SVG for this chart carries a `data-s="2.5,4,3,5,..."` series
  labelled "(size-weighted points)". `series.weekly_buckets` (2F, the
  function the task brief names for this) counts rows per week - it has no
  parameter for a per-row weight, and adding one would mean editing a file
  this task does not own. Rather than fake a size-weighted series by
  duplicating rows per point value (which would also skew the 12-week
  *shape*, not just its unit), the sparkline is built on
  `series.weekly_buckets(person_merged_prs, "merged_at", weeks=12)` and
  labelled honestly - "Delivered, 12 weeks (PRs merged)" - a real count, not
  a mislabeled approximation of the mockup's weighting.

## Non-code rubrics render their reason, not a fabricated table

- `_components_for_person` returns `(None, lookup, None)` whenever the
  person's role is not in `roles.CODE_ROLES`, even when `lookup.status ==
  "scored"` (QA-automated, QA-manual, PM, designer, infrastructure all have
  a `Rubric` in `roles.py` since 2C, but - per `docs/assumptions/2C.md` -
  "none of these five rubrics has a component-computation function behind
  it yet ... that's future work"). The scorecard panel for such a person is
  a `callout()` naming the rubric and saying so plainly, never an invented
  component breakdown built from data the rubric was never designed to
  read. Exec, no-rubric roles (seo/wine/advisor) and unmapped people go
  through the same `None` path with their own `roles.RubricLookup.reason`.

## Table rows and the row-level "never a zero for a missing measurement" rule

- Every table cell is built by a small formatter (`_score_cell_html`,
  `_delivered_cell_html`, `_cycle_cell_text`, `_reviews_cell_text`,
  `_estimate_cell_html`, `_flags_cell_html`) that checks `pd.isna` first and
  renders `"—"` before ever formatting a number - this holds for every row,
  not conditionally on whether that row happens to be under the measurable
  floor, so there is no code path where a genuinely-missing figure prints
  as `0`. A real, informative zero (2B's own rule: `flag_count`/
  `reviews_given`/`delivered_points` are real `0`s once their source
  pipeline ran and found nothing) still prints as `0` deliberately, per
  `people_table.py`'s own documented distinction - `tests/test_people.py`
  asserts both halves of that distinction directly
  (`test_delivered_cell_distinguishes_missing_from_a_real_zero`,
  `test_flags_cell_gray_zero_vs_dash_for_no_changelog`).

## Avatar colour and role display

- `_avatar_hue` cycles the eight `s1`..`s8` series tokens by
  `hash(person) % 8` rather than a hand-kept name-to-colour map (the
  mockup's own table hand-picks one per row) - deterministic within a
  process, no maintenance burden as the roster grows, and every hue still
  routes through `theme_html._hue_var` so it repaints with `theme_tokens.py`
  automatically. Exec, no-rubric and role-unknown rows get the muted
  `"gray"` hue instead (`_hue_var("gray")` resolves to `var(--ink-4)`),
  matching the mockup's own treatment of Igor/Angel/Arsalan's avatars.
- Role labels come from `roles.ROLE_LABELS` (2C), not a second copy kept in
  this file.

## Sort order and the role filter

- `_sorted_table` orders by role, then score descending (unscored people
  sort after every scored person in the same role, via a `-1.0` fill for
  `pd.NA` scores), then person name - matches the mockup's own per-role
  grouping with the highest performer first.
- `_role_filter_options` builds `"All roles"` plus one pill per role
  actually present in the table (not the full 16-key `roles.ROLE_ORDER`
  list) - a role with nobody scored on it today does not get a pill that
  filters to an empty table. `st.pills` is `selection_mode="single"` with
  `default="All roles"`; a caller narrowing to a specific label filters the
  already-built `people_table` frame in Python (`shown = table_df[table_df["role"]
  == selected_role]`) rather than re-querying anything, since the table was
  already fetched once for the whole roster.

## The person selector is separate from the existing `?person=` deep link

- `_one_person_instead(bundle, view, slot)` is called first, unchanged,
  exactly as every other engineering page does - a reader who arrives via a
  link naming one assignee still gets the full Streamlit-native
  `_render_individual_page` (sprint capacity, personal PR sections, the
  weekly-delivery bar chart), which is a different, larger view this task
  was not asked to replace. The new `st.selectbox` "Person" control is a
  second, independent way to reach a scorecard - for browsing the roster
  table itself, not for the "this whole page is now about one engineer"
  deep link.

## Testing approach

- No Streamlit `AppTest` harness exists in this repo (confirmed by grepping
  `tests/` - `pages/delivery.py`'s and `pages/today.py`'s own "renders
  end-to-end" tests use the same pattern this task follows). Two layers:
  small pure functions (every cell formatter, `_role_filter_options`,
  `_sorted_table`, `_components_for_person`, `_evidence_rows`,
  `_jira_search_url`/`_github_search_url`) are tested directly against
  crafted `pandas` objects and the real default roster; a handful of
  full-page tests stub `_EngineeringData`/`_EngineeringView` the same way
  `tests/test_delivery_page.py::_render_page` does and capture every
  `st.markdown` fragment the page writes, asserting on the resulting HTML.
  `st.pills`/`st.selectbox` are monkeypatched in the full-page tests to
  control which role/person is selected; left un-monkeypatched (as in the
  `theme_html.py`-level smoke test above), both widgets work fine in
  Streamlit's "bare mode" and return their first option - verified by hand
  before relying on it in `test_the_page_renders_end_to_end_on_an_empty_frame_without_raising`.
