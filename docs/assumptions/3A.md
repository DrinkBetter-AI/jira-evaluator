# Task 3A assumptions — the Today page, full HTML

One bullet per ambiguous call, what was chosen, and why.

## Kept the pre-3A Streamlit functions, unchanged, alongside the new HTML ones

- `_decision_card` and `_render_attention_band` (the old `st.container`/
  `st.progress`/`st.columns` hero and decide cards) are **still defined,
  unchanged, and no longer called by `_render_today_page`.** The task said
  "keep every existing test in that file passing; add to it, do not rewrite
  it" - and `tests/test_today.py` already pins `_render_attention_band`'s
  exact structure (three regression tests from Task 2G: the decide cards
  must render on the happy path, must still render when the hero raises, and
  the function's two `try` blocks must each carry exactly one `except`).
  Rewriting `_render_attention_band` to build HTML risked breaking those
  pinned assertions for no reason - they test a function, not a page. The
  live page now builds its hero/decide-card HTML through two new functions,
  `_hero_fragment`/`_decide_cards` (fragment builders) and
  `_hero_and_decide_fragment` (the try/except wrapper that reproduces the
  2G fix - a broken hero must not take the decide cards down with it - for
  the new HTML path). Both old and new versions are tested; only the new one
  renders.

## Tile set: Median cycle time, not Ownerless

- The mockup's six "This week" tiles are Tickets resolved, PRs merged,
  Median cycle time, Open tickets, Stalled, Estimate coverage. The pre-3A
  page had Ownerless in the sixth slot instead. The mockup wins, per the
  task brief. Ownerless is not lost - it is still one of the three decide
  cards (`∅ Ownership`) and still drives its own action queue in "Do these
  next"; it just is not also a KPI tile.

## No historical board-state snapshot exists anywhere in this codebase

This is the load-bearing fact behind every sparkline/delta decision below.
Confirmed by reading `snapshot.py` (which records a page's own *drawing*, for
PDF export - not the board's state over time) and by grepping the rest of the
codebase: nothing persists "how many tickets were open, or estimated, or
stalled, as of date X". `series.weekly_buckets` only counts rows in a frame
by a date column - it has no aggregate (median/ratio) primitive and no way to
answer "what was the board's shape at a past instant" for a metric that is
inherently a snapshot rather than an event. Two tiles (Tickets resolved, PRs
merged) are literally weekly event counts, so `tickets_resolved_series`/
`prs_merged_series` apply directly. The other four needed a judgment call:

- **Tickets resolved · 7d / PRs merged · 7d** - straightforward:
  `series.tickets_resolved_series`/`prs_merged_series` over a dedicated
  12-week (84-day) fetch (see below). Delta compares the last two *full*
  calendar weeks in the bucket series (`buckets[-2]` vs `buckets[-3]`),
  never the partial current week (`buckets[-1]`) against a full prior
  week - `docs/assumptions/2F.md` names this exact trap and puts the fix on
  the caller, since `delta()`'s signature takes plain numbers with no
  knowledge of `WeekBucket.is_partial`.

- **Median cycle time** - delta comes straight from
  `integrity.end_to_end_cycle`'s own current/baseline pair
  (`median_days` vs `baseline_median_days`, `higher_is_better=False`), not a
  fabricated week-over-week reconstruction - that pair *is* the real,
  already-designed-for-this comparison. `baseline_days` is set to
  `12*7/2 = 42`, so the function's current + baseline windows together cover
  exactly the same 84 days already fetched for the throughput series (its
  own default, 90, would ask for 180 days of resolved-ticket history this
  page has no other reason to hold). The **spark**, though, needs 12 points,
  and there is no weekly-median primitive in `series.py` to call for one -
  only a weekly-*count* primitive. `_weekly_median_days` is a small,
  page-private function (duplicating `series.py`'s private `_week_start` in
  miniature, since that name is not public to import) that buckets
  `end_to_end_cycle`'s own `detail` rows (real finish dates + real day
  counts) by calendar week and takes the median per week, forward/back-
  filling (`ffill`/`bfill`) any week with no finished ticket in it rather
  than drawing a fabricated zero (which would read as "resolved instantly").

- **Open tickets** - the tile's *value* is the current open count
  (`len(df)`, a real snapshot). Its **spark and delta are a different, real
  signal**: `series.weekly_buckets(df, "created", 12)`, i.e. how many of the
  *currently open* tickets were created in week N - backlog inflow, not a
  reconstructed total-over-time. This is a legitimate, non-fabricated
  design (stock shown as the value, flow shown as the trend) but it is
  worth stating plainly: the spark does not literally chart the number in
  the tile above it. `higher_is_better=False` on the delta (rising creation
  volume is a "watch this" signal, not unambiguously bad) is a judgment
  call, not a certainty - flagged here rather than left silent.

- **Stalled 30d+** - same reasoning as Open tickets: no way to reconstruct
  "how many were stalled as of week N", so `_stalled_weekly` buckets each
  *currently* stalled ticket's own age (`now - age_days` ≈ when it crossed
  the threshold) into weeks instead - a real "when did today's stalled
  tickets go stale" distribution, not a snapshot history. `higher_is_better=
  False`: more tickets newly crossing the threshold in a week is a real,
  legitimate bad signal, and this is the literal case the task brief names
  ("stalled tickets up is bad").

- **Estimate coverage** - `_estimate_weekly_ratio` computes, per week,
  what share of the policy-applicable tickets *created* that week currently
  carry an estimate - a real cohort ratio, not a reconstructed
  coverage-at-time-N. Returns two parallel series: the raw ratio (`None` for
  a week with no policy-applicable ticket created in it - a genuine "no
  data" gap, not a zero) for the **delta**, and the same series
  forward/back-filled for the **spark**, which cannot draw a `None`. This is
  the tile exercised by `test_a_tile_whose_prior_period_has_no_data_
  renders_neutral`'s sibling case in spirit; the test file uses Median cycle
  time for that assertion instead, because `end_to_end_cycle`'s own
  `baseline_median_days=None` path is the cleaner, already-designed "no
  prior data" signal to construct in a test.

## A dedicated, wider Jira/GitHub read for the 12-week chart

- The bundle's opening reads only carry 30 days of resolved tickets
  (`resolved_30`) and 30 days of merged PRs (`merged_prs`) - sized for the
  per-person pie on other pages, not a 12-week trend. Rather than draw a
  chart where 8 of 12 weeks are structurally zero, `_fetch_resolved_window`/
  `_fetch_merged_window` (in `pages/today.py`, not `data_layer.py`) call the
  same `data_layer.fetch_resolved_tickets`/`fetch_merged_prs_cached`
  functions with `days=84` directly. This is not a new read *mechanism* -
  it is the identical pattern `render_shared._render_weekly_delivery`
  already uses to get one person's 12-week history, applied org-wide. Both
  underlying functions are already `st.cache_data`-cached for 5 minutes, so
  a second render in that window costs nothing further. Kept as two thin,
  separately-mockable functions (`_fetch_resolved_window`/
  `_fetch_merged_window`) specifically so tests never need a real Jira
  credential or GitHub token.

## Links: hero and decide cards only, not tiles or bars

- `theme_html.Tile` and `theme_html.Bar` have no link/href field in the
  frozen 1B contract - only `hero()` and `decide_cards()` accept a `link`/
  `action`. "Every number that can link to the underlying Jira/GitHub query
  should link" is therefore satisfied exactly where the mockup itself draws
  a link (the hero's "See stuck PRs →" and each decide card's "→" action),
  and nowhere else on this page - not a shortfall, the kit's own shape.
- The hero's link is a real GitHub search
  (`org:{org} is:pr is:open draft:false review:none`), not the mockup's
  literal `href="#"`. GitHub's search syntax has no qualifier for "has
  reviews but none approving" (the hero's actual "unapproved" number) -
  only `review:none` ("nobody has reviewed this at all", the harsher
  `never_reviewed` subset). Linking to the nearest real, correct query was
  judged better than either inventing an unsupported filter or leaving a
  dead `#` link; the gap between what the number says and what the link
  searches for is recorded here rather than silently glossed over.
- The Triage and Ownership decide-card links are real Jira "Issue
  navigator" URLs built from the page's own JQL plus a status/assignee
  filter (`_jql_search_url`), reusing `render_shared.JIRA_BROWSE_BASE` (the
  same vetted, http(s)-only site URL every ticket link on the app already
  uses) rather than a second, separately-configured site value.

## `series` imported at module top, breaking the page's own local-import convention

- `docs/assumptions/1C.md` documents that each page module keeps only
  stdlib/pandas/streamlit/theme/theme_html/data_layer/render_shared at
  module top, importing every analytics module (`hygiene`, `next_actions`,
  `integrity`, `github_client`, …) inside the specific function that needs
  it. `series` is imported at the top of `pages/today.py` instead, as a
  deliberate, noted exception: it is used in nearly every Task 3A function
  below (`_throughput`, `_tiles`, `_stalled_weekly`,
  `_estimate_weekly_ratio`, `_delta_text`), and it is as dependency-free as
  `theme_html.py` itself (no Streamlit import, no project-internal import
  besides `pandas` - see `series.py`'s own module docstring). Every other
  new import in this file (`github_client`, `integrity`, `next_actions`,
  `hygiene`) stays function-local, matching the existing convention.

## "Do these next" stays exactly as it was

- `_render_next_actions` (the expander/dataframe queues with clickable
  `LinkColumn`s) is unchanged and still called from `_render_today_page`,
  between the hero/decide row and the tiles. The task brief's own MODE
  section allows this explicitly: "Where a reader needs interaction... the
  page keeps Streamlit widgets beside them." This section is not in the
  mockup at all (it predates the mockup, added to answer "a count is not a
  move" - see the section's own docstring), so there was no HTML form to
  match it against, and no acceptance criterion asked for one.
