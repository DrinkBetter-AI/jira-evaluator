# Task 2G assumptions

One bullet per ambiguous call, what was chosen, and why.

- **Bug 1, fault 2 (dead second `except`): removed, not narrowed.** The task
  offered two options - remove it, or narrow the first clause so the second
  becomes reachable. Removed it. There was no second distinct failure mode
  for the try to distinguish: both clauses caught `Exception` and both did
  the same thing (`logger.exception(...)`; `st.error(...)`), just with
  different log messages ("PR section" vs "decision cards"). Narrowing the
  first clause to something specific (e.g. catching only errors from the
  `prs.get(...)` calls) would have meant inventing a boundary between "hero
  errors" and "decision-card errors" that the code never actually had - the
  decision cards don't call anything that can fail the way the hero body
  can (they only format already-validated arguments the caller passed in).
  One handler covering the one try that can genuinely fail (the hero body)
  is the honest shape.

- **Bug 1, fault 3: column allocation got its own try, not just moved outside
  every try.** The task allowed either "move it out of the try" or "bind the
  names before it". A bare move (assign `hero, a, b, c` above the try with no
  guard at all) would fix the literal `NameError` - the names are always
  bound before the hero try runs - but leaves a new failure mode: if
  `st.columns()` itself ever raises (not the described bug, but the thing
  the description flags as the risk at that line), the whole function raises
  uncaught, and the three decide cards - the page's actual point - never
  render at all. Wrapping the allocation in its own try with a fallback
  (`hero = a = b = c = st.container()`) means the decide cards render even in
  that case, degraded (stacked in one container instead of three columns)
  rather than absent. This is what "an exception raised before the column
  allocation still produces a rendered page" in the acceptance criteria is
  read to require - a rendered page, not just an absence of `NameError`.

- **`_render_attention_band`'s hero try still swallows and shows `st.error`,
  same as before.** Not asked to change; only the three faults listed were in
  scope. The hero degrading to an error message while the decide cards next
  to it keep working is the intended shape post-fix, not a leftover bug.

- **Scorecard "Score" column: plain formatted strings (`"n/a"` / `"80"`), not
  a numeric column with `NaN` for insufficient rows.** Tried `NaN` first
  (compatible with `st.column_config.ProgressColumn`, which renders it as a
  blank bar) but rejected it: a blank/empty progress bar and a bar at 0% look
  the same at a glance, which is exactly the failure this fix exists to
  close - a column that has to be *read carefully* to avoid mistaking
  "not measured" for "measured at zero" is still the bug, just moved from
  text to pixels. A plain string column that says `n/a` in the cell can't be
  misread that way. Cost: the `ProgressColumn` visual bar is gone for every
  row, not just the insufficient ones, since a single column can't mix a
  numeric progress bar with text cells. Tried and confirmed by hand that
  mixing `int` and `"n/a"` in one object-dtype column crashes `st.dataframe`
  outright (`pyarrow.lib.ArrowInvalid: Could not convert 'n/a' ... tried to
  convert to int64`), so this wasn't a "nicer to look at" choice over that
  option - that option doesn't run.

- **Measurable-denominator wording: "Overall {score:.0f} over
  {covered_weight:.0f} measurable points", read literally from the task's own
  example ("Overall 81 over 95 measurable points").** `score` (from
  `kpi.overall`) is a weighted mean already expressed on a 0-100 scale, not a
  raw point sum, so "81 over 95" is not dimensionally a fraction - it's the
  headline number relabeled against the honest denominator instead of a flat
  100. That is what was asked for, not a change to how `score` itself is
  computed (`kpi.overall` is owned by another agent's file, `kpi.py`, and is
  out of scope here regardless).

- **New caption computes `covered_weight / total_weight` itself rather than
  printing `covered_weight` alone as "N% measurable".** `kpi.WEIGHTS` happens
  to sum to exactly 100 today (confirmed: 10+10+20+15+10+10+10+10+5=100), so
  `covered_weight` and a percentage are numerically identical right now - but
  the caption computes the ratio explicitly instead of assuming that
  coincidence holds forever, since `kpi.py`'s weights are owned by a
  different agent and could change under this code.

- **`kpi.coverage(parts)` is called once, after `kpi.overall(parts)`, not
  merged into a single call.** `kpi.overall` and `kpi.coverage` both walk the
  same `parts` list independently (confirmed in `kpi.py`: `overall` filters
  `p.sufficient` and sums weighted scores; `coverage` filters `p.sufficient`
  and sums weights) - recomputing `coverage` here is a second cheap pass over
  a list of at most nine `Component` objects, not a second Jira/GitHub read,
  so there was no reason to thread `Coverage` through `kpi.overall`'s
  signature (owned by another agent) just to save that.

- **Did not turn on `include_gaps=True` anywhere.** Out of scope - the task
  says this is latent until "the People page" turns it on in "the next
  phase", and `kpi.components`'s default and every current caller are owned
  by other agents' files (`kpi.py`, and whichever page eventually calls
  `_render_scorecard` with gaps on). The guard is defensive: it is correct
  today (no `sufficient=False` rows exist yet, so it changes nothing
  observable), and it is correct the moment gaps are switched on, without
  this file needing to change again.

- **Tests reach `pages/today.py` internals via a direct `from pages import
  today` import in `tests/test_today.py`, not through `app.__getattr__`.**
  `app.py`'s `_PAGE_PRIVATE_REEXPORTS` dict (see `docs/assumptions/1C.md`)
  only lists five specific names from `pages/today.py`
  (`_ownerless`, `_ownerless_rows`, `_estimate_coverage`, `_action_queues`,
  `_ACTION_QUEUE_NAMES`); `_render_attention_band` and `_decision_card` are
  not on it, and adding names to that dict would mean editing `app.py`, which
  this task does not own. `tests/test_today.py` is owned here, so it imports
  the page module directly instead.

- **Bug-1 regression tests force a hero failure via `monkeypatch.setattr(
  today.st, "progress", boom)` rather than by passing malformed `prs`.**
  Malformed input (e.g. `prs=None`) would test "the hero survives bad data",
  a different property than "the hero survives an exception partway through
  rendering" - which is what the pre-split bug was actually about (an
  exception, from any cause, partway through the `with hero:` block). Forcing
  the failure at a real `st.*` call inside that block is the more faithful
  reproduction and doesn't require inventing an invalid `prs` shape the real
  caller (`_render_today_page`, via `_open_pr_signals`) would never produce.

- **Bug-1 "dead except clause" fault is pinned structurally (via `ast`, one
  `except` handler per `try`), not behaviorally.** By definition, truly dead
  code produces no observable difference in output - that's what makes it
  dead. A behavioral test that happened to pass before this fix would
  therefore also pass against a version with the dead clause silently
  restored, which defeats the point of a regression test for that specific
  fault. The `ast` check fails immediately if a second stacked handler is
  ever reintroduced on either try in the function.
