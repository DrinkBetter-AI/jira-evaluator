# Task 2A assumptions — flow honesty and attribution (WP3)

One bullet per ambiguous call, what was chosen, and why. Function-level
docstrings in `integrity.py`, `prioritization.py` and `data_layer.py` carry the
detailed reasoning and each function's own blind spot; this file is the index
of decisions plus the wiring work Phase 3 still has to do.

## Decisions

- **`idle_days` → `status_age_days` is opt-in, not automatic.** `add_priority_score`
  and `assignee_rollup` (`prioritization.py`) now accept an optional `events`
  argument. When it is supplied, the staleness term and the `stale_15d_plus`
  queue count are driven by `integrity.status_age_days` instead of `idle_days`,
  and `masked_days` / `avg_masked_days` / `avg_status_age_days` /
  `max_status_age_days` are added to the output. When it is **not** supplied
  (every call site today - see "Render call sites for Phase 3" below), both
  functions fall back to exactly the old `idle_days`-driven numbers and the old
  column schema, unchanged. The alternative - always requiring `events` - would
  have broken every existing caller's signature in one edit; the alternative of
  silently keeping `idle_days` until every caller is rewired would have shipped
  nothing this iteration. Opt-in lets the honest math exist and be tested now,
  wired in incrementally by whoever owns each render file.

- **`idle_days` stays visible everywhere, as "last touched".** No call site had
  `idle_days` removed from its output; only what *scores* off it changed. The
  task said to keep it visible, and it is also still the only staleness number
  some callers (not yet wired) will ever see.

- **Former-staff list: env wins, `ROSTER.md`'s list is the fallback, not a second
  source of truth.** `integrity._former_staff_from_env` reads
  `JIRA_FORMER_STAFF` (semicolon-separated, matching `roles_template.env`) and
  falls back to a frozenset copied from `ROSTER.md`'s "Former / inactive" list
  only when the env var is unset or empty. If the env var is set but to a
  different (e.g. trimmed or corrected) list, the env value is used as-is with
  no merge - the deployment's own value is assumed authoritative once it
  exists.

- **No import of the in-flight `roles.py`.** Another agent is building a fuller
  roster object in this same iteration window. Importing it from `integrity.py`
  would make this module's tests depend on that module having landed first
  (or at all) and would violate `integrity.py`'s own documented rule of staying
  free of imports from the rest of the app. `_former_staff_from_env` is a
  ~10-line private parser instead. **Consolidate into `roles.py` once it
  ships** - `integrity.py` should import the roster's former-staff set from
  there rather than parsing the env a second time.

- **Former-staff resolutions are flagged, not dropped.** `credited_resolutions`
  keeps every resolution authored by someone on the former-staff list in
  `detail` (`is_former_staff=True`, `credited=False`, `reason="former_staff"`),
  and still lists that person in `by_person` with `credited_resolutions=0` and
  `flagged_resolutions>0` rather than omitting them entirely. This matches the
  module's existing anti-silent-drop convention (`integrity_flags` does the
  same for every other flag) and gives a manager the "this account is still
  authoring transitions" conversation instead of a number that just quietly
  changed.

- **Unattributed resolutions treat `""` and `"Unknown"` as the same signal.**
  `changelog_events` always writes the literal `"Unknown"` when a history
  entry's `author` object is missing or empty - it never writes `""`. But a
  caller building an events frame directly (a test, a changelog read from
  something other than `changelog_events`) shouldn't have to know that exact
  sentinel spelling to be counted correctly, so `unattributed_resolutions` and
  `credited_resolutions` both treat a blank string the same as `"Unknown"`.

- **`org_reopen_rate`'s denominator is "distinct tickets that entered a
  resolved status in the window"**, computed the same way
  `reresolve_events` computes it (so the two numbers can never quietly
  disagree about what "resolved in the window" means), not Jira's
  `fetch_resolved_count` (a different, server-side, non-changelog count).
  `share` is `None` only when that denominator is zero; a real zero reopens
  over a real nonzero denominator is `0.0`, not `None` - the acceptance test
  spells out why this distinction matters.

- **`end_to_end_cycle`'s "current" window is the same length as `baseline_days`**
  (no separate `window_days` parameter). The task named a single parameter
  (`baseline_days=90`), so "current" = the last `baseline_days` days and
  "baseline" = the `baseline_days` before that, rather than inventing a second,
  independently-tunable window the task didn't ask for.

- **`fetch_resolved_tickets` (`data_layer.py`) now requests `expand="changelog"`.**
  This is the only way to compute credited resolutions without a second Jira
  read: the function already fetches every ticket resolved in the window, and
  the changelog for those same tickets is what the credit join needs. The
  `assignee` field it already carried was left in place (not removed) so the
  new `credited_resolvers` join can show "credited to X, board still shows Y"
  when the two disagree - that gap is itself useful evidence, not noise to
  delete. `FETCH_SCHEMA_VERSION` was bumped 8 → 9 so a cache entry written
  before this change (no `changelog` column) is not served to the new join.

- **`credited_resolvers` is a plain function, not a second `@st.cache_data`
  read.** The Jira read it depends on (`fetch_resolved_tickets`) is already
  cached; the join itself is in-memory work over at most `max_results` rows,
  the same order of cost `_derive_board`'s changelog parse already pays once
  per board read. Caching it separately would add a second cache-key surface
  for no measurable benefit.

## Render call sites for Phase 3

Everywhere the wiring above needs a caller to actually pass `events` (or
switch to the new join) to take effect. None of these files are owned by this
task; edit them in Phase 3.

1. **`data_layer.py:_derive_board`** (line ~1114, `add_priority_score(add_ticket_health_fields(raw_df))`)
   — should become `add_priority_score(add_ticket_health_fields(raw_df), events=events)`,
   where `events` is the `integrity.changelog_events(raw_df)` result computed two
   lines above in the same function. This is the one call site that would turn
   on honest staleness for the whole board's `priority_score`/`priority_rank`
   and every downstream sort that reads them. **Not touched here** because
   `data_layer.py`'s file scope for this task was the credit-attribution join
   only, and this line sits inside `_derive_board`, outside that join.

2. **`render_shared.py:2004`** (`add_priority_score(estimate_policy(df, BACKLOG_STATUSES))`,
   inside the sprint-planning render path) — same change: pass `events` from
   whatever bundle the caller already has (`bundle.events` from
   `_engineering_data()`), so sprint planning ranks tickets by real staleness
   too.

3. **`render_shared.py:1007`** (`_render_scope_breakdown`, `rollup = assignee_rollup(scoped)`)
   — pass `events` here so the assignee-breakdown table's `stale_15d_plus`
   count and the new `avg_status_age_days`/`avg_masked_days` columns appear.
   The table is drawn with `st.dataframe(rollup, ..., column_config={...})`
   with no explicit column allow-list, so the new columns will render
   automatically once `events` is passed - Phase 3 should add `column_config`
   entries for them (`avg_status_age_days`, `max_status_age_days`,
   `avg_masked_days`) so they get proper labels instead of raw snake_case
   headers.

4. **`pages/engineering.py:_render_resolved_summary`** (the "Who resolved
   tickets (30 days)" ranking, fed by `data.get("resolved_30")` at line ~755)
   — this is the exact render path behind the "194 resolved, second highest in
   the company" artefact. It currently does
   `resolved_df["assignee"].value_counts()`. Replace with
   `data_layer.credited_resolvers(data.get("resolved_30"))`, rank
   `credit.by_person` by `credited_resolutions` instead, and surface
   `flagged_resolutions`/`is_former_staff` somewhere on the same panel (a
   caption, a second small table, or a filter toggle) rather than dropping
   those rows silently - the whole point of the flag is that it stays visible.

5. **`render_shared.py:4465`** (`_stalled_rows`, the "Today" page's stalled-ticket
   queue) — **already correct**, included here only so Phase 3 doesn't
   duplicate it: it already calls `integrity.status_age_days(df, resolved_events)`
   and falls back to `idle_days` only on a parse failure, with the fallback
   labelled `"edge age (no changelog)"` in its own return value. Use this as
   the reference pattern for wiring the other call sites above.

## Other modules that read `idle_days` and are not wired (out of file scope for 2A)

Listed for completeness, not acted on — none of these files are in this task's
"files you own" list, so editing them was out of scope here. Whoever picks up
the rest of this wiring should start from this list rather than re-discovering
it by grepping.

- `hygiene.py:stale_candidates` — the `DEFAULT_STALE_DAYS=90` "abandoned
  ticket" queue used by the cleanup page. Same exploit as `assignee_rollup`'s
  `stale_15d_plus`: a label edit resets `idle_days` and buys a ticket out of
  this list.
- `kpi.py` (lines ~302, ~377, ~511 in the pre-2A file) — the scorecard's
  "Weekly updates" and "Staleness" components, and the "Urgent response" /
  "Fresh board" badge, all read `idle_days` directly. `kpi.py` is on this
  task's do-not-touch list.
- `cleanup.py` (line ~51) — per-ticket idle threshold feeding triage-queue
  sorting.
- `pr_hygiene.py` (`stale_idle_days`) — PR staleness, not ticket staleness;
  a different (GitHub `updated_at`-derived) `idle_days` column entirely, so
  this one is not actually gameable the same way, but is worth a second look
  before assuming it is fine.
- `epics.py`, `teams.py`, `epic_organization.py` — idle-days-based sorting and
  aggregation in the epic and team roll-up views.
- `next_actions.py` — already has the right shape
  (`STALLED_AGE_COLUMN if STALLED_AGE_COLUMN in stalled.columns else "idle_days"`),
  i.e. it prefers a pre-computed honest age column when the caller supplies
  one and only falls back to `idle_days` otherwise. Callers that pass it a
  frame from a `status_age_days`-aware source get the fix for free; callers
  that don't, don't.

## What was NOT changed

- `integrity.status_age_days`, `reresolve_events`, `status_pingpong`,
  `cosmetic_touches`, `estimate_churn`, `cycle_time`, `integrity_flags` are all
  pre-existing (built before this task) and untouched beyond the module
  docstring's function index at the top of the file.
- `FLAG_NAMES` / `integrity_flags` were not extended with a fifth flag for
  former-staff credit or unattributed resolutions. The task's acceptance
  criteria test the new functions directly; adding a flag would be a
  reasonable Phase 3 follow-up (e.g. `unattributed_credit` alongside the
  existing four) but wasn't asked for here and would touch the flag-evidence
  formatting this task didn't need to change.
