# Task 3C assumptions

One bullet per ambiguous call, what was chosen, and why. All changes are to
`pages/delivery.py`, `tests/test_delivery_page.py`; nothing outside those
files (and this doc) was touched.

## The three replaced tiles: what each one actually counts

- **Two different event scopes, chosen per tile, not one blanket "org
  events" frame.** `bundle.events` only carries changelog for tickets the
  board's JQL still returns (`statusCategory != Done`) — a ticket that fully
  closed drops out of it, and with it every entry/exit it ever made through a
  resolved-class status (`Review in Staging`, `Ready for Production`, ...).
  2A's `fetch_resolved_tickets`/`data.get("resolved_30")` is the other half:
  every ticket that entered a resolved status in the trailing 30 days,
  changelog included, whether it is still open or fully closed now.
  - **Staging round-trips** uses `bundle.events` alone
    (`_staging_round_trips`). This tile's headline value and its delta are
    read off the *same* population on purpose, so a real, honest
    current-vs-prior-30d comparison is possible: `bundle.events` carries each
    open ticket's entire history, unbounded by any fetch window, so slicing
    it at "now" and at "now − 30d" compares like with like. Mixing in
    `resolved_30` (which only ever covers the trailing 30 days) would make
    the prior slice systematically thinner than the current one and turn
    every delta into a fake "improvement" — see the next bullet for why that
    same move is *not* taken for Reopened.
  - **Reopened · 30d** and **Unattributed** both use
    `_combined_org_events(bundle.events, resolved_30)` (concatenated, deduped
    on `(key, entry_id)`). Reopened's whole point is a share of a real
    resolved population ("a count without its denominator is not a fact" —
    the task's own words), and `bundle.events` alone would make that
    denominator almost meaningless (most tickets that actually finished have
    left the open-ticket JQL scope entirely). Unattributed uses the same
    combined frame for consistency with Reopened rather than a third,
    differently-scoped population.
  - **Blind spot, stated once for both:** a ticket that fully resolved and
    closed more than 30 days ago is invisible to either frame — the same gap
    every other org-wide figure on this page that leans on `resolved_30`
    already has.

## Deltas: real where computable honestly, explicitly "no data" where not

- **Staging round-trips gets a real delta.** Current and prior 30-day counts
  are both read from `bundle.events` (see above), so the comparison is
  apples-to-apples. `higher_is_better=False` (more bouncing is worse).
- **Reopened and Unattributed's deltas are structurally "no prior data"
  (`prior=None`, passed explicitly to `series.delta`).** An accurate current
  value needs `resolved_30` (trailing 30 days only); an accurate *prior*
  30-day slice would need "tickets that entered a resolved status 31–60 days
  ago", which no cached fetch in this page's ownership provides. Building one
  from `bundle.events` alone (the only always-available frame) would compare
  the headline value against a differently-scoped prior number — exactly the
  "delta computed on a different population than the number it's attached
  to" trap the rest of this codebase's integrity functions go out of their
  way to avoid. `series.delta(current, None, higher_is_better=False)` gives
  `direction="flat"`, `is_good=None` — renders neutral, never green, and
  still carries an explicit direction, satisfying the acceptance bullet
  without inventing a number. This matches the mockup's own choice for these
  two tiles (`— flat` / `—`), for what it's worth.
- **`Resolved · 7d` gets a delta too**, even though the task's acceptance
  list only names the three new tiles — "add deltas everywhere" and the
  task's own "throughput up is good" example both point at this tile. The
  prior side is approximated: `resolved_7` itself
  (`data.get("resolved_count_7")`) is the exact, uncapped org-wide count and
  is what the tile's value shows; there is no equivalent exact fetch for
  "resolved 7–14 days ago", so the prior side is read from `resolved_30`
  (already fetched, capped at `max_results` like every other figure derived
  from it) — an approximation of the prior week, not a second exact count.
  `higher_is_better=True`.
- **`Median In-Progress` gets no delta.** Computing one honestly would need a
  timestamped baseline split of `integrity.cycle_time`'s closed intervals
  (current vs. prior window), which is new statistical machinery beyond
  "port three tiles" on a page marked "closest to done... a precision job,
  not a rebuild". Left unchanged from before this task.

## Cold start: "no changelog data read" beats a bare 0

- When `bundle.events` **and** `resolved_30` are both empty (no changelog was
  read at all — a genuinely empty board, or a cold-start render before any
  data landed), the three new tiles show `—` with the note "no changelog
  data read" instead of running the real computation and printing an
  org-wide `0`. A real `0` here ("this org has never had a staging
  round-trip") and "we haven't read anything yet" are different facts, and
  conflating them is exactly the failure mode the rest of this page (the
  stale table's `stale_unreadable` flag, the cycle chart's "not enough
  closed intervals" message) already refuses to make. This is the literal
  mechanism behind the "says so rather than showing zeros" acceptance bullet.

## `theme_html.tiles()`'s `write=True` cannot be combined with the new `Tile` form

- Read literally, `tiles(cards, *, write=None, ...)` sets
  `is_legacy = write if write is not None else (auto-detect)`. Passing
  `write=True` therefore forces the *legacy* tuple-unpacking branch
  unconditionally — regardless of whether `cards` holds `Tile` objects — and
  crashes trying to unpack a `Tile` NamedTuple as a 4-tuple. `theme_html.py`
  is out of this task's ownership, so the fix is on this page's side: call
  `tiles(...)` with no `write` argument (auto-detects the new form from
  `cards[0]` being a `Tile`), capture the returned fragment string, and hand
  it to `theme_html.render()` explicitly — the pattern 1B.md itself
  recommends ("build fragments with `tiles()`/`hbars()`/`table()`, hand them
  all to `render()`").

## Porting the stale table to the new `table()` form

- `theme_html.table()`'s new form (`Column`/`Cell`) returns only the bare
  `<table>` fragment — no card, no title (1B.md: "no generic `card()`
  function in this file... composition is the caller's", confirmed by
  `test_table_new_form_returns_a_bare_table_not_a_card`). A page-private
  `_card()` was added to `pages/delivery.py` that reproduces
  `theme_html._legacy_table_html`'s card markup exactly (same class names,
  same title/subtitle/footer placement, `html.escape` instead of reaching
  into `theme_html._esc`, a private name in a file this task does not own) so
  the port changes nothing the reader sees. Column kinds, order and labels
  (`Ticket`/link, `Summary`/text, `Owner`/text, `Status`/text, `Status age`
  /num, `Last touched`/num, `Masked`/num) are unchanged from the legacy call.
- The ranking itself (`status_age_days`, never `idle_days`), `idle_days`
  staying visible as "Last touched", and `masked_days` as the gap between
  them were **already correct** before this task — `_stale_with_masked` and
  `_stalled_rows` already follow 2A's item 5 ("already correct... use as the
  reference pattern"). Nothing about *what* the table ranks on or shows
  changed; only the `theme_html` call shape did.

## Page shell: `page_header()` / `section()` / `foot()`

- No other page module wires these three yet (checked: zero call sites
  outside `theme_html.py` itself and its own tests as of this task). Added
  here per the task's explicit instruction. `page_header`'s `freshness`
  string is built by a small page-private `_freshness_caption()` rather than
  importing `app._board_age_caption` (private to `app.py`, and importing
  from `app` would be the exact circular import Task 1C's split exists to
  prevent) — it reads the same `data_layer._ENGINEERING_DATA_AS_OF_KEY`
  session-state key `app.py`'s version reads.
- `app.py`'s `main()` already draws `st.title(PAGE_HEADINGS[...])` for every
  page (out of this task's ownership). Adding `page_header()` here means the
  page briefly shows both a plain Streamlit title and the mockup's HTML brand
  row — a known, visible duplication, not silently worked around by editing
  `app.py`. Left as-is; a later task that owns `app.py` is the place to drop
  one of the two once every page has its own `page_header()`.
- `hbars()` (the two chart panels) was **left in its legacy form**. The task
  named the stale table specifically for the `table()` port; porting `hbars`
  too was not asked for and was left out to keep this a precision change
  rather than a rebuild.

## Kept for backward compatibility, no longer called

- `_stalled_count` stays defined, byte-identical, even though
  `_render_delivery_page` no longer calls it (its tile — `Stalled Nd+` — was
  one of the three removed). `app.py`'s `__getattr__` re-export list
  (`docs/assumptions/1C.md`) names `pages.delivery._stalled_count` by string;
  deleting the function would silently break `app._stalled_count` for any
  test or caller still reaching it that way, and `app.py` is out of this
  task's ownership to fix up.
