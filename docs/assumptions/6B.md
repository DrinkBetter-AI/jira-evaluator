# Task 6B assumptions — standup truth-check (WP10)

One bullet per ambiguous call. Function-level docstrings in `standup.py` carry
the detailed reasoning and each function's own blind spot; this file is the
index of decisions.

## Decisions

- **No live Fireflies integration is exercised anywhere.** There is no key in
  this environment and none is expected during this task, so
  `fetch_standup_truth_check` is written and reviewed but never actually run
  against the real API. It's covered by two tests: no key set (returns
  unavailable immediately, no request attempted) and key set but the request
  raising (degrades the same way). The GraphQL query shape
  (`id`/`date`/`participants`/`meeting_attendees`/`speakers`/`sentences` with
  `ai_filters`) is written from Fireflies' public schema, not verified against
  a live response — the first real key that gets configured should be treated
  as this query's first real test, not just the module's.

- **Commitments come only from `ai_filters.task`, not a keyword heuristic.**
  Fireflies tags sentences it thinks are a commitment. `extract_action_items`
  trusts that flag and does not additionally scan for "I'll"/"going to"-style
  phrasing. A keyword fallback would manufacture quotes attributed to people
  on a team already sensitive to being accused unfairly (see the alias-table
  rationale below); a transcript with no `ai_filters` at all just yields zero
  action items for that transcript, and that's stated as a blind spot in the
  docstring rather than silently patched over.

- **The alias table is seeded with one confirmed entry (`tina` → `Dina QA`,
  plus `gina` as the same known mishearing), not a larger guessed list.** The
  task says to build the table "data-driven and easy to extend" — it does not
  say to pre-populate it with plausible-looking entries for every accented
  name on the roster (Anouar, Santi, Mihai, etc.). Guessing likely
  mishearings without a transcript to point at is exactly the "reads as an
  accusation" failure mode the task warns about. The table is one dict
  literal with a comment explaining the sourcing bar for a new entry;
  extending it is a one-line PR once a human confirms a specific mishearing.

- **Roster resolution checks the roster before the alias table, not after.**
  `resolve_speaker` tries an exact case-insensitive roster match first. This
  means a correctly-transcribed name is never accidentally routed through an
  alias, and it means the alias table only ever fires on a name that
  genuinely isn't in the roster as spelled — the intended failure mode
  (Fireflies mangled it), not a shortcut around a normal match.

- **`active_roster_names` is a required, separately-passed argument — never
  derived from the transcript.** The task is explicit that `participants` is
  untrustworthy for *identity*; I've extended that to mean it also cannot be
  used to build the *expected-attendee pool* for absence detection, even
  though nothing in the task literally forbids that second use. Deriving
  "who was expected today" from `participants` would resurrect Dat (and every
  other departed name still sitting in standup invites) as a phantom
  no-notice absentee on every future standup — the exact failure this task
  exists to prevent, just moved one function over. The caller (the Integrity
  page, when this gets wired in) is expected to pass `roles.py`'s live active
  roster.

- **"Notice" is detected only from the transcript itself — no external notice
  source.** I considered accepting an injected list of `(person, date)` pairs
  representing OOO/Slack notices from elsewhere, but nothing in this repo
  currently produces such a list, and building a placeholder for a source
  that doesn't exist yet would be speculative. Instead, `no_notice_absences`
  scans the same meeting's sentences for another speaker naming the absent
  person alongside a fixed phrase list (`ABSENCE_NOTICE_PHRASES`). This is
  documented as a floor, not a ceiling, in the function's own docstring: a
  notice given over Slack or worded outside the phrase list reads as
  "no notice" here even when notice existed. If a real notice source shows up
  later (calendar OOO, a Slack integration), it should be joined in as an
  additional signal, not a replacement for this one — an absence nobody
  mentioned on the call is still worth asking about even if OOO was filed.

- **Jira ticket-key matching defines its own regex** (`TICKET_KEY_RE`,
  `[A-Z][A-Z0-9]{1,9}-\d{1,6}`) rather than importing one. `pr_hygiene.py` has
  an equivalent pattern (`_GENERIC_KEY_RE`), but it's underscore-private and
  `pr_hygiene.py` isn't a file this task owns or should take a dependency on
  mid-iteration while another agent may be editing it. The two patterns match
  the same key shape; worth consolidating into a shared constant later, not
  during this task.

- **The changelog join tries ticket-key match before falling back to
  author-activity match, and labels which one fired (`matched_by`).** A named
  ticket is much stronger evidence than "this person touched some status
  somewhere in the window" — collapsing both into one boolean would let a
  vague, unnamed commitment ("I'll get to it") read as confirmed just because
  its speaker happened to close an unrelated ticket that week. Keeping the
  column lets a consumer choose to trust only the strong signal.

- **Outcome vocabulary is `{"followed_through", "open"}` only — no third
  state and no negative-sounding label.** The task is explicit that an
  unmatched item is "open, not a lie." I considered adding a third state for
  "matched but to the wrong ticket" (e.g., a typo'd key) but there's no way
  to distinguish that from a genuinely different but plausible ticket without
  guessing intent, so a typo'd or wrong key currently just reads as `open`
  (no match found) — consistent with the module's stated job of reporting,
  not concluding.

- **This module does not attempt to identify which Fireflies meeting *is* the
  standup versus some other recurring call.** `attendance_summary`'s
  docstring states the assumption plainly: the `transcripts` sequence passed
  in must already be one consistent meeting series, because the denominator
  for attendance rate is just `len(transcripts)`. Filtering `fetch_standup_truth_check`'s
  Fireflies query to the standup specifically (by title, calendar ID, or
  similar) is Integrity-page wiring work, out of scope for this task's four
  owned files.

- **Nothing here is wired into `app.py` or any page.** The task's file list
  is `standup.py`, `tests/test_standup.py`, `docs/assumptions/6B.md` only.
  `KPI_SPEC.md` §5's "Phase 3 — needs you" / admin-gated Integrity panel
  wiring (reading `roles.py`'s roster, calling `truth_check`, rendering the
  result) is left for whoever owns that page.
