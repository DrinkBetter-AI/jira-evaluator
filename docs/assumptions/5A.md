# Task 5A assumptions

One bullet per ambiguous or judgment-call decision made during the design
conformance sweep, plus the reasoning a reviewer would otherwise have to
reconstruct from the diff.

## `theme_html.tiles()` / `hbars()` `write` bug

- **`write` made orthogonal to input shape.** Both functions used to decide
  "legacy tuple form vs. new `Tile`/`Bar` form" by looking at the `write`
  argument instead of the argument list itself, so `tiles(new_form_cards,
  write=True)` silently rendered the legacy branch and crashed. Fixed by
  detecting shape purely from `cards[0]`/`bars[0]`'s type
  (`isinstance(..., Tile)` / `isinstance(..., Bar)`), then treating `write`
  as a pure "did I already print it" flag. This also quietly fixed the
  mirror-image bug (`write=False` forcing the new-form branch on legacy
  tuples), which nothing had exercised before.

## Duplication removed

- **KPI tiles: one system, not two.** `theme.kpi_strip()` /
  `page_shared._kpis()` were a structural duplicate of
  `theme_html.tiles()` - same concept (a row of value + delta cards),
  different markup and CSS classes. Migrated both call sites
  (`render_shared._render_team_overview`'s Sprint tiles,
  `pages/engineering.py`'s Ticket-health tiles) to
  `theme_html.tiles([Tile(...), ...])` and deleted `kpi_strip()` and
  `_kpis()` entirely, along with the `.kpi-strip`/`.kpi-card` CSS block.
- **Not migrated, deliberately: `page_shared._tile()` / `st.metric()`.**
  `pages/business.py` builds its tiles on Streamlit's native `st.metric`
  (through `page_shared._tile`), which is a different rendering mechanism
  entirely (a real Streamlit widget, not an HTML fragment) used throughout
  that page for its delta-arrow and colour behaviour. Rewriting every
  `business.py` tile onto `theme_html.tiles()` would be a structural rewrite
  of that page, which is out of bounds for a conformance sweep ("don't
  restructure a page's information architecture"). Instead the actual
  conformance violation living inside that mechanism - the delta-arrow
  colour bug - was fixed in place (see below). The KPI-tile consolidation
  is therefore scoped to the one true duplicate, not to every place a tile
  appears.
- **Chips: one system.** `theme.py`'s `.triage-meta` markup, the invented
  per-stage colour dict in `render_shared.py` (`_STAGE_COLORS`), and the
  tier legend's own hex table were all re-implementations of
  `theme_html.chip()` / `theme_html.legend()`. `_render_status_pills()` and
  `_tier_legend_html()` now call `theme_html.chip()` / `theme_html.legend()`
  against `theme_tokens.STAGE_TONES` and a derived `_TIER_TONE` map instead
  of carrying their own colour tables.
- **Triage card chip, done without importing `theme_html`.** The triage
  card's own chip markup was rewritten to reuse the shared `.card`/`.chip`
  CSS classes and CSS custom properties directly (hand-built HTML string,
  wrapped in `<div class="vv">...</div>`) rather than calling
  `theme_html.chip()`. This was a deliberate exception to "consolidate to
  one `chip()`": `tests/test_planning_page.py::
  test_the_triage_flow_source_has_no_html_kit_dependency` pins that
  `_render_triage_card`'s and `_render_cleanup`'s source contains no
  reference to `theme_html` at all, and that test belongs to a different
  agent's file ownership (`render_shared.py` is mine, but the test asserting
  this constraint predates this task and encodes a real design decision -
  the triage flow should not gain a dependency on the HTML component kit).
  Reusing the same CSS classes/custom properties gets the visual
  consolidation (one chip look, one colour source) without violating that
  pin.
- **Severity colour ramp: one function.** `pages/code.py`'s
  `_share_rank_bar` had its own literal four-colour severity ramp
  (`#e34948`/`#eb6834`/`#eda100`/`#1baf7a`) duplicating
  `theme_html._bar_color`'s thresholds exactly. Extracted the threshold
  logic into `theme_html.severity_hue(value) -> str` (returns a `theme_tokens`
  series key, not a raw hex) and pointed both call sites - `theme_html`'s
  own bar colouring and `code.py`'s - at it through
  `theme_tokens.SERIES_BY_KEY`.

## Accent colour dropped on migrated tiles

- `theme_html.Tile` has no value-accent field by design (a tile's colour
  comes from its delta direction/goodness, not from a static "is this
  number good" judgement baked into the tile itself). Migrating
  `render_shared.py`'s Sprint tiles and `pages/engineering.py`'s
  Ticket-health tiles onto `theme_html.tiles()` therefore drops the old
  red/green static accent those tiles used to carry. This is intentional,
  not a regression: a static count coloured red/green with no delta
  baseline was itself an unearned-colour bug of the same shape the
  delta-arrow rule targets - colour was standing in for a judgement the
  data didn't actually support.

## Delta-arrow colour bug (the core conformance violation found)

- **`pages/business.py::_delta_arrow` always used `delta_color="normal"`**,
  which colours a *rising* value green regardless of whether rising is
  good. Three cost tiles (Ads Spend, Google Cloud, OpenAI) therefore
  coloured a rising cost green - the exact "green arrow on a rising stall
  count" failure mode named in the task brief. Fixed by adding a
  `higher_is_better` parameter to `_delta_arrow` and threading
  `higher_is_better=False` through the three cost tiles.
- **"Biggest drop-off" used `delta_color="inverse"` on a literal negative
  magnitude** (not a period-over-period change), which flips red/negative
  to green - colouring a loss of users as good news. Fixed to
  `delta_color="normal"`, which keeps a negative number red.
- Audited every `series.delta()` call site that feeds `Tile(delta_dir=...)`
  (`pages/delivery.py`, `pages/today.py`) and found they already wired
  `delta_dir`/`delta_good` from the two separate `Delta` fields correctly -
  no bug there, but added a regression test
  (`test_every_tile_with_a_delta_direction_also_carries_a_separate_goodness`)
  so a future edit can't collapse them back into "colour = direction."

## Bar geometry (24px / 4px rule)

- **`bargap` is a fraction of the row slot, not a pixel value** - a fixed
  `bargap` cannot hold bars at a fixed pixel ceiling once the chart's
  height floor (`max(240, ...)`) inflates the per-row slot for small `n`.
  Added `theme.bar_gap_for(n_rows, plot_height)`, which solves for the
  bargap fraction that keeps every row's bar at or under
  `BAR_MAX_HEIGHT` (24px) regardless of how much the height floor inflates
  the slot. Applied to both `theme.rank_bar` and
  `pages/code.py::_share_rank_bar`, and both got `marker.cornerradius =
  BAR_CORNER_RADIUS` (4px) for the rounded data-end.

## Hero number

- **`theme_tokens.HERO_SIZE = 48`** added as a rung above the six-size type
  ladder, specifically for the one-hero-per-page rule, rather than reusing
  the top ladder rung - the hero is not "the biggest label," it is a
  distinct visual category with its own minimum.
- `pages/today.py`'s hero span was `font-size:44px` (below the 48px floor)
  and used a literal hex (`#64748b`) alongside it; both fixed to
  `theme.TYPE_HERO` / `theme_tokens.INK["3"]`.
- `pages/today.py` keeps two dead functions (`_decision_card`,
  `_render_attention_band`) that are not called by the live page - the live
  path is `_hero_fragment` / `_decide_cards`. They are pinned by
  `tests/test_today.py` (owned by another agent's earlier task) and left in
  place rather than deleted, per "don't break a test pinning real behaviour
  unless the conformance rule genuinely conflicts with it." The hero-count
  test (`test_today_page_draws_exactly_one_live_hero`) excludes this dead
  source before counting, so it checks what the page actually renders.

## Content max-width

- `theme_tokens.MAX_WIDTH` and `theme.CONTENT_MAX_WIDTH` were already both
  `"1280px"` pre-task; the conformance test
  (`test_content_max_width_is_1280px_everywhere_it_is_declared`) makes that
  agreement load-bearing by asserting both constants, the CSS custom
  property, and scanning every swept module's source for a conflicting
  literal `max-width:` declaration (excluding the one legitimate
  exception: prose measure `70ch` on the type-ladder's reading-width rule,
  which is a different property in the same reformatting-radius rule and
  not a content-width violation).

## Conformance-test exemptions

- **`theme_html.py` is excluded from the literal-hex and off-ladder-font
  sweeps.** It carries the mockup's own chrome greys (already covered and
  justified by `tests/test_theme_html.py`) and legitimate 11-12px
  decorative micro-text (`.chip`, `.dim`, `.av`, `.rolechip`, `.nnote`,
  SVG axis labels) copied verbatim from the source mockup's own
  stylesheet. These were never part of the original "type is too small to
  read" complaint the type ladder exists to fix, and papering over them
  with fake ladder rungs would make the ladder lie about what sizes are
  actually in play.

## Pinned test changed (documented, per house rule: conformance wins)

- **`tests/test_theme_visual.py::
  test_the_type_scale_is_a_ladder_rather_than_a_pile_of_sizes`** used to
  assert every `TYPE_*` rung appears literally inside `theme._STYLE`.
  Deleting the `.triage-card .triage-summary` CSS rule (part of the
  `.triage-card` duplication removed above) removed the only place
  `TYPE_SECTION` (20px) appeared in that stylesheet - it now lives as an
  inline `theme.TYPE_SECTION` reference in `pages/today.py` instead.
  Rewrote the test to accept a rung either appearing literally in
  `theme._STYLE` **or** being referenced as `theme.<NAME>` from any file
  under `pages/` or from `render_shared.py`, so the ladder rule still holds
  ("every declared rung is actually used somewhere, off a single source of
  truth") without insisting every rung's use is CSS specifically.

## Test-isolation bug found and fixed (blocking a green suite, not a content change)

- **`tests/test_price_charts.py::
  test_bigger_text_keeps_the_colours_the_app_already_drew_with`** had an
  order-dependent failure: its `finally` block unconditionally deleted
  `theme._TEMPLATE` from `plotly.io.templates` after restoring
  `pio.templates.default`, but if another test in the same process had
  already registered that template and left `pio.templates.default`
  pointing at it, the unconditional delete left a dangling default -
  `ValueError: Invalid value... 'vinovoss'` in whichever test ran next.
  Fixed by snapshotting whether the template existed before this test ran
  and only deleting it in `finally` if this test was the one that created
  it. Verified deterministic across repeated full-suite runs.

## `engineer_letter.py`

- Kept its `TIER_COLOURS` dict as literal hex values (per that module's own
  stated contract: stdlib-only, no import of `theme_tokens`, so it stays
  portable/dependency-free) but updated the literals to match the new
  derived `render_shared._TIER_BG` (via `theme_tokens.STATUS_BG`) so the two
  stay visually identical, with a comment on each line citing the
  `theme_tokens` source it was copied from. `tests/test_engineer_letter.py`
  pins `engineer_letter.TIER_COLOURS == dashboard._TIER_BG`, so both sides
  had to change together.
