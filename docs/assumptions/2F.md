# Task 2F assumptions

One bullet per ambiguous call, what was chosen, and why.

- **Week anchor**: calendar weeks, Monday 00:00:00 **UTC**, not local time and
  not a rolling trailing-7-days window. Every timestamp is converted to UTC
  before its week is computed, which is what makes the same instant land in
  the same bucket for a teammate in Vietnam (UTC+7), Uruguay (UTC-3), Tunisia
  (UTC+1) or the EU (UTC+2) - the test asserts this directly by expressing one
  pinned instant in all four offsets. UTC (not, say, "whatever `st.session_state`
  thinks the viewer's timezone is") was chosen because it is the one anchor
  that does not depend on who is looking at the page, and because Jira and
  GitHub both already hand back UTC timestamps - no conversion-on-write is
  needed anywhere else in the pipeline.

- **`BOT_LOGINS` not imported from `render_shared.py`**: the task allowed
  this fallback explicitly if the import were circular. It is not circular
  *today* - `series.py` is new and nothing yet imports it - but `render_shared`
  is exactly the module that will need to call into `series.py` to paint the
  Today sparklines and deltas, almost certainly on this same branch, given six
  other agents are editing this tree concurrently. Importing `render_shared`
  (which pulls in `streamlit` and ~4,700 lines at module scope, confirmed by
  running `import render_shared` standalone - it prints a page's worth of
  Streamlit cache-runtime warnings just from that) from a small, dependency-free
  module like `series.py` would also invert the layering every other business
  module here uses: `pr_quality.py`, `estimate_accuracy.py` and `integrity.py`
  none import `render_shared`, `render_shared` imports them. `series.py` took
  the parameterised fallback instead: `bot_logins` is an explicit argument on
  both series builders, defaulting to a local `DEFAULT_BOT_LOGINS` that reads
  the same `GITHUB_BOT_LOGINS` env var `render_shared.BOT_LOGINS` reads, so the
  two lists agree at runtime without a Python import between them. Whoever
  wires this into the Today page should pass `render_shared.BOT_LOGINS`
  explicitly at the call site to keep exactly one source of truth in view.

- **`date_col` default for `tickets_resolved_series`**: `status_category_changed_date`,
  not a `resolutiondate`-style field, because no such field exists on the
  frame `fetch_resolved_tickets` returns - `RESOLVED_FIELDS = ("assignee",)`
  and the row builder in `jira_client.py` never populates a resolution
  timestamp. `status_category_changed_date` is the closest machine-recorded
  stand-in already carried on every row. This is an approximation, not the
  changelog-accurate "every CHANGED TO a resolved status" event
  `render_shared._weekly_resolved_buckets` derives from the full changelog via
  `integrity.changelog_events` - reusing that machinery here would mean
  bucketing by ticket-changelog-entries rather than by a single frame date
  column, which is a different (and heavier) shape than the
  `weekly_buckets(frame, date_col, weeks)` signature the task specified. A
  ticket that re-enters a resolved status more than once (KPI_SPEC exploit #2,
  "mint resolutions in staging") is under-counted here - it shows only its
  most recent category change, not every re-entry. `integrity.reresolve_events`
  is the tool that already catches that; this module doesn't duplicate it.

- **`date_col` default for `prs_merged_series`**: `merged_at`, and the
  function does not itself filter to merged rows - it assumes the caller
  passes a frame already scoped to merged PRs, the shape
  `data_layer.fetch_merged_prs_cached` / `github_client.fetch_merged_prs`
  returns (queried with a merged-PR search, not filtered client-side).
  `pr_quality._merged_mask` exists for a frame that mixes merged and unmerged
  rows, but it is a private, underscore-prefixed name in a module `series.py`
  otherwise has no reason to import; if a future caller needs to hand this
  function a mixed-state frame, filtering with `pr_quality._merged_mask` (or
  `state == "MERGED"`) before calling `prs_merged_series` is the caller's job.

- **`delta()` `magnitude` is a raw absolute difference, not a percentage**:
  percentage change is undefined at `prior == 0`, and `prior == 0` is not a
  rare edge case here - a metric going from zero to nonzero (a new hire's
  first PR, the first ticket in a newly-created category) is exactly the kind
  of week a CEO wants a delta tile to describe clearly, not divide-by-zero on.
  A caller that wants a percentage can compute one from `magnitude` and the
  two source values and add its own zero-guard; this function does not invent
  one silently.

- **`delta()` on a genuine tie** (`current == prior`, both known, not missing):
  `direction="flat"`, `is_good=None` - not `True` and not `False`. Nothing
  changed, so calling it "good" or "bad" would be an invented verdict. This is
  a distinct code path from the missing-prior-data case (also `is_good=None`,
  also reported as `direction="flat"` since there is no direction to point an
  arrow at) but the two are reached through different inputs and
  `magnitude` tells them apart on inspection: `0` for a genuine tie, `None`
  for missing data. Both must fail the same `is_good is True` check a renderer
  uses to decide whether to paint a tile green, which is the property the
  acceptance test asserts directly.

- **`delta()`'s partial-current-week interaction with `weekly_buckets`**: not
  resolved automatically. `weekly_buckets`'s last bucket is always partial
  (the current, still-open week), and `delta(current_bucket.value,
  prior_bucket.value, ...)` will structurally read as "down" most of the week
  simply because the current week has fewer days of data in it than the prior
  full week - not because output actually fell. `delta()` has no way to know
  it was handed a partial bucket; it is the caller's job to compare a partial
  current week against a same-length prior slice (e.g. "so far this week" vs.
  "the same weekday last week"), not against a full prior week's total. Noted
  here rather than silently guarded against, because guarding against it
  inside `delta()` would require `delta()` to know about `WeekBucket` at all,
  which the signature the task specified (`delta(current, prior)`, plain
  numbers) does not allow for.
