## What moved where

- `app.py` (6,847 → 502 lines): imports needed by what's left, the
  business-page lazy-wrapper block (unchanged), one lazy dispatch wrapper per
  engineering page (`_render_today_page` etc., mirroring the pre-existing
  `_render_business`), a `__getattr__` hook for page-private test helpers
  (below), `_PageSpec` / `_page_specs` / `_pages`, `main()`, and the small
  helpers `main()` needs (`_board_age_caption`, `_reads_debug_enabled`,
  `_render_page_reads`).
- `render_shared.py` (new, ~4,700 lines): every helper called by two or more
  of the six page-render functions, computed by building the actual call
  graph (see below) rather than guessing - see the frozen API above.
- `pages/today.py`, `pages/people.py`, `pages/delivery.py`, `pages/code.py`,
  `pages/planning.py`, `pages/engineering.py` (new): each page's own
  `_render_*_page` plus whatever helper only that page calls.
- `pages/business.py`: untouched.

## Decisions

- **How "called by 2+ pages" was decided, not guessed.** Built the literal
  call graph (regex over each top-level function's body, resolved
  transitively) from all six page-render functions
  (`_render_today_page` … `_render_engineering_page`) and classified every
  helper by how many of the six reach it. `_render_engineering_page` (the
  legacy `/engineering` page) turned out to be a near-superset of the five
  focused pages, so most helpers ended up in `render_shared.py` - that is a
  real property of the code, not an artifact of the method: Engineering
  really does draw almost everything the other five pages draw individually,
  including drilling into `_render_individual_page` through
  `_one_person_instead` exactly as People/Delivery/Code/Planning do.

- **Decorator-boundary bug caught and fixed before extraction.** A naive
  "def-line to next-def-line" range split attaches a leading `@st.fragment`
  decorator to the *previous* function's range, not the one it decorates.
  Caught this by checking all 19 `@st.fragment` occurrences against their
  destination file before writing anything, and fixed the range builder to
  walk back over contiguous `@...` lines above each `def`. Four of the 19
  would otherwise have been silently misattached (`_render_metrics`,
  `_render_mix`, `_render_scope_breakdown`, `_render_resolved_summary`),
  which would have decorated the wrong function as an `st.fragment` and
  correctly-decorated the wrong one as a plain function.

- **Trailing-constant boundary bugs, same root cause, found by an explicit
  audit.** A module-level constant sitting between function A's body and
  function B's `def` line is captured in A's range even when only B uses it.
  Audited every constant assignment between lines 231-6604 against its real
  users; found two real cases and fixed them: `_PRIORITY_BUCKET_MAP` /
  `_BUCKET_COLORS` (used only by `_render_bubble_chart`, engineering-only;
  moved from `render_shared.py` to `pages/engineering.py`) and
  `_DEFAULT_BOT_LOGINS` / `BOT_LOGINS` (used only by `_is_bot`, shared; moved
  from the business block to `render_shared.py`). Everything else audited
  matched its owner correctly.

- **`_clear_page_caches` moved to `render_shared.py`, not listed as
  "stays in app.py"** even though the task's explicit stay-list doesn't name
  it. It's called directly from inside `_render_sprint_capacity` and
  `_render_triage_decisions` (both shared, both in `render_shared.py`) as
  well as from `main()`, so leaving it in `app.py` would make
  `render_shared.py` import from `app.py` - backwards, and circular given
  `app.py` already imports `render_shared`. It keeps its own tiny
  `_lazy_import_business()` (a copy of `app.py`'s, not a shared one) so it
  doesn't need to import `app.py` either.

- **Page-dispatch wrappers in `app.py` are not literally in the "stays"
  list either, but are required by it.** `_page_specs()` (which is in the
  stays-list) passes `_render_today_page` etc. as bare callables to
  `_PageSpec` / `st.Page`; those names have to resolve to something in
  `app.py`. Added one four-line lazy wrapper per page, exactly mirroring the
  pre-existing `_render_business` (`_business_readable`/`_render_business`
  already used this pattern before Task 1C). Each wrapper's `from pages
  import X` runs only when that page is actually navigated to - matching the
  "Lazy imports" rule ("app.py must import page modules lazily... inside the
  page's render dispatch") to the letter, since these wrapper functions *are*
  the render dispatch `st.Page` calls into.

- **Backward-compat re-exports: two mechanisms, chosen by whether the name's
  owner is a page module.** For names in `render_shared.py` (not a page
  module - the task's laziness rule targets pages only), `app.py` imports
  them normally at module top, exactly like it already does for
  `page_shared` and `data_layer`. For the handful of names private to one
  *page* module that a few tests still reach as `app._name`
  (`_ownerless`, `_ownerless_rows`, `_estimate_coverage`, `_action_queues`,
  `_ACTION_QUEUE_NAMES` from `pages/today.py`; `_cycle_by_status`,
  `_stale_with_masked`, `_stalled_count` from `pages/delivery.py`;
  `_team_prs`, `_render_code_kpis` from `pages/code.py`), a module-level
  `__getattr__` (PEP 562) resolves them on first access instead - this keeps
  `app.py`'s own top level free of any `pages.*` import, satisfying "app.py
  must import page modules lazily... inside the page's render dispatch, not
  at the top of app.py" for these too, while `app._name` still works for the
  handful of tests that use it. The apptest harnesses' monkeypatch targets
  (`dashboard.cost_client.load_stripe_env = ...` etc.) needed the actual
  client modules (`ads_client`, `amplitude_client`, `cost_client`,
  `github_client`, `merchant_client`, `orders_client`) importable as plain
  `app.<name>` module references too - these are cheap bare-module imports
  (no page-module import involved) and were added at `app.py`'s top,
  matching how they reached `dashboard.<client>` before the split.

- **"Import discipline" (function-local heavy imports) applied to the six
  new `pages/*.py` files, not to `render_shared.py`.** Confirmed first that
  `page_shared.py` - a hard, unavoidable dependency of the code that stays
  in `app.py` (`BOARD_ASKED_KEY`, `_reset_reports`, `_deliver_board_snapshot`
  etc.) and out of this task's ownership - already imports pandas, plotly,
  every analytics module (`kpi`, `capacity`, `cleanup`, `teams`, `epics`,
  `hygiene`, `next_actions`, `pr_hygiene`, `pr_quality`, `prioritization`,
  `sprint_planner`, `ticket_quality`, `write_access`, `engineer_letter`) and
  every client module (`ads_client`, `amplitude_client`, `cost_client`,
  `github_client`, `merchant_client`, `orders_client`, `vivino_client`) at
  its own top level. `import app` therefore cannot avoid pulling those in
  regardless of anything done in `render_shared.py` or the page modules -
  verified: `import page_shared` alone puts `plotly` and `pandas` in
  `sys.modules`, before this task changed a single line. Given that,
  `render_shared.py` keeps the same top-level import block `app.py` carried
  before the split (it is the direct successor of that code, and hand-moving
  every one of ~90 functions' dependencies to per-function local imports for
  zero measurable benefit was not a good use of the risk budget on a
  behavior-identical mechanical split). The six page modules get the real
  treatment: each keeps only stdlib, `pandas`/`numpy`, `streamlit`, `theme`,
  `theme_html`, `data_layer` and `render_shared` at module top; every
  analytics module (`hygiene`, `teams`, `next_actions`, `transformations`,
  `write_access`, `change_audit`, `integrity`, `pr_hygiene`, `pr_quality`)
  and `plotly` is imported inside the specific function that uses it. This
  is the meaningful win: none of the six pages pulls in another page's
  dependencies, and `import app` does not get *worse* than the
  `page_shared.py`-forced baseline - confirmed both before and after by
  diffing `sys.modules` after a bare `import app` (0.82s either way; same
  module set either way, since `page_shared` already forced the ceiling).

- **`TRIAGE_STUCK_HOURS` is a `data_layer` constant, not a `hygiene` one** -
  found this while wiring up `pages/today.py`'s, `pages/planning.py`'s and
  `pages/engineering.py`'s local imports; `hygiene.py` has no such name.
  Imported it from `data_layer` (already a required top-level import in all
  three files) instead of adding a needless local import.

- **`tests/test_price_charts.py::test_every_chart_states_its_own_text_size`
  updated, not routed around.** This test enumerates every file capable of
  drawing a chart (its own comment says so: "Phase 8 split the dashboard
  across these modules... all of them are in scope for this check") and
  counts `theme.plot(` calls across that list. Task 1C moved chart-drawing
  code out of `app.py` into `render_shared.py` and the six `pages/*.py`
  files, so the file list is now stale in exactly the way its own comment
  anticipates - not a case of routing around a broken extraction. Added the
  seven new files to the tuple; left the `>= 11` threshold and all other
  logic untouched.
