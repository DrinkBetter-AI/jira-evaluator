# Task 4 assumptions — the Integrity page and its access control

One bullet per ambiguous call, what was chosen, and why.

## Access design: two independent gates, registration by configuration, identity by session

- **A second credential, checked nowhere near the first.**
  `access_gate.require_password()` (the existing shared `DASHBOARD_PASSWORD`
  gate, checked once in `app.py::main()` before any page runs) stays exactly
  what it was: the door every hourly contractor already has a key to.
  `access_gate.require_admin_password()` is new, reads a second env var
  (`DASHBOARD_ADMIN_PASSWORD`), keeps its own session-state key
  (`_admin_access_granted`, distinct from the main gate's `_access_granted`),
  and is never referenced by the main gate or vice versa. Knowing one teaches
  nothing about the other — proven by
  `test_the_shared_password_alone_does_not_grant_admin_access`.

- **No local-dev bypass for the admin credential, unlike the main gate.**
  `require_password()` skips the gate entirely when `DASHBOARD_PASSWORD` is
  unset and the process isn't on Cloud Run (`K_SERVICE` unset) — reasonable
  for a shared password guarding write access on a laptop only the developer
  can reach. That reasoning does not extend to a page that names people and
  shows padding evidence: `admin_password_configured()` /
  `admin_access_granted()` / `require_admin_password()` all return `False`
  unconditionally when `DASHBOARD_ADMIN_PASSWORD` is unset, in every
  environment, including local. `admin_access_granted()` checks the env var
  **before** looking at session state for exactly this reason — a stale or
  tampered `_admin_access_granted=True` left in session state cannot grant
  access once the credential is unset out from under it
  (`test_an_unset_admin_password_fails_closed_even_with_a_stale_session_flag`).

- **`_PageSpec` registration is gated on *configuration*
  (`DASHBOARD_ADMIN_PASSWORD` set), not on *this session already being
  authenticated*.** This was the real design fork, and it resolves a
  structural puzzle the task brief doesn't spell out: if `_page_specs()`
  only advertised the Integrity spec once a session had already proven the
  admin password, nobody could ever reach the page to *type* the password on
  in the first place — Streamlit only routes a URL to a page that was
  already part of that session's very first `st.navigation()` call (its own
  `Page.visibility` docs say so explicitly), so a page absent from that
  first call is unreachable by URL for the rest of that session, full stop.
  Gating on configuration instead — the same structural pattern
  `_business_readable()` already uses, checking env presence rather than any
  session's identity — makes `/integrity` reachable for anyone, on any
  session, the moment the deployment sets the credential; per-session
  identity is then enforced completely separately and unconditionally by
  `require_admin_password()` inside `pages/integrity.py`'s own render
  function. This is also what keeps `tests/test_pages.py`'s
  `test_every_page_has_a_heading_of_its_own` green without touching
  `render_shared.py`'s `PAGE_HEADINGS` (off this task's file list): that test
  runs with `DASHBOARD_ADMIN_PASSWORD` unset in the default test
  environment, so `_integrity_readable()` is `False` and the spec — which
  has no `PAGE_HEADINGS` entry — is simply absent from the list that test
  iterates.

- **What "does not appear in the nav for a non-admin session, appears for an
  admin one" means given the above.** Read literally against Streamlit's
  actual `visibility="hidden"` semantics (excluded from the nav menu for
  *every* session once registered, admin or not — confirmed by reading
  `st.Page`'s own docstring in this environment), a session-scoped nav
  distinction isn't the mechanism in play; hidden is a static property of
  this one spec, set once, for everyone, which is what
  `_integrity_readable()`'s docstring and the `_page_specs()` comment above
  it now say plainly. The real, tested distinction is at the content level:
  a session without the admin credential that reaches `/integrity` sees
  nothing but `require_admin_password()`'s sign-in prompt (or, if the
  credential isn't configured at all, a hard-disabled error) — never the
  four cards, never a call into `integrity.py`. A session with the
  credential sees the real page. `test_an_admin_session_renders_cards_and_
  calls_the_flag_functions` and
  `test_a_non_admin_session_never_calls_into_integrity_or_pr_quality` are
  the two tests that make this concrete; the latter is the one the task
  brief calls out as the test that matters most.

- **`require_admin_password()` is a return-value gate, not solely a
  `st.stop()`-and-hope.** Verified empirically in this environment:
  `st.stop()`, `st.rerun()`, `st.error()`, `st.text_input()` all no-op
  (return harmlessly, `text_input` returning `""`) outside a live Streamlit
  script run — there is no `ScriptRunContext` in a bare pytest process, and
  Streamlit's own bare-mode warning says as much. A gate that relied purely
  on `st.stop()` halting the script would pass every test trivially (nothing
  after `st.stop()` would look reachable) without proving anything about a
  live deployment, and — worse — would not actually stop a bare invocation
  from falling through to the rest of the function. `require_admin_password()`
  therefore both calls `st.stop()` in every failing branch (so a live
  Streamlit run halts at the prompt, belt-and-suspenders) **and** returns
  `False`/`True` explicitly, and `pages/integrity.py::_render_integrity_page`
  branches on the return value (`if not access_gate.require_admin_password():
  return`) rather than trusting `st.stop()` alone. This is also exactly why
  the imports of `integrity`/`pr_quality`/`roles`/`data_layer` inside
  `_render_integrity_page` are placed *after* that `if`, as local imports —
  a non-admin session's call into the function returns before Python even
  executes those `import` statements, so the modules are provably never
  touched, not merely never called into.

- **The gate's position is pinned by a structural test, not just a
  behavioural one.** `test_the_gate_is_the_functions_first_real_statement`
  parses `_render_integrity_page`'s source with `ast` and asserts its first
  statement after the docstring is exactly `if not
  access_gate.require_admin_password(): return`. This exists because the
  spy-based test alone (mocking `require_admin_password` to return `False`)
  would keep passing even if a future edit moved the gate check to, say,
  after a cheap-looking but real board read — the spy would still show zero
  calls into `integrity.py` specifically, while `data_layer._engineering_data()`
  quietly started running for every visitor. The `_boom` stub wired into
  `data_layer._engineering_context` in the "zero calls" test catches that
  exact regression too (it raises if reached at all), and the `ast` test
  pins the ordering itself so a reviewer sees the guarantee in the test
  suite, not only in a comment.

## The four cards

- **Roll-up first, cards second.** `integrity.integrity_flags` is rendered
  as its own top card (`_rollup_card`) — a compact per-person table of which
  of the four named flags they tripped, in the last `_FLAGS_WINDOW_DAYS`
  (30, matching `integrity_flags`'s own default) — directly above the
  `.intgrid` two-column grid of the four detailed cards. This is "the
  roll-up it was designed to be" read literally: a summary that points at
  the detail cards below it for evidence, rather than a fifth thing
  competing with them.

- **Card 1 (`_freshness_card`) baselines cosmetic touches within role,
  computed from the same window's data, not a separate historical read.**
  `roles.load_roster()` supplies `role_of(person)`; the baseline for a role
  is the *median* cosmetic-touch count among everyone else sharing that role
  who shows up in this same `cosmetic_touches()` call's output. A role with
  fewer than two people represented in that data (Infra, PM, ML — all
  effectively solo per `ROSTER.md`) falls back to the org-wide median rather
  than comparing a person only to themselves, which would always read as
  zero excess regardless of how large their raw count is —
  `test_a_role_with_too_few_peers_falls_back_to_the_org_median` pins this.
  Ranking is by `excess_vs_role` (count minus baseline), not raw count, which
  is what makes `test_a_pm_with_many_grooming_touches_does_not_outrank_an_
  engineer_with_few` hold: a PM's absolute count can be far higher than an
  engineer's and still rank below it once each is measured against their own
  role's normal.
  - One thing this baseline cannot see, stated for the record rather than
    solved here: it is a floor for how many people share a role, not a
    matter of statistical power. Two PMs is still two data points; the
    fallback to the org median is a deliberate, documented approximation,
    not a claim that two-person medians are trustworthy.

- **Card 2 (`_estimate_card`) aggregates `estimate_churn`'s per-edit rows to
  one row per author**, summing `delta_hours` for `direction == "raised"`
  edits only (lowered/set/cleared/unchanged are out of scope for a padding
  signal by construction — see `estimate_churn`'s own docstring). Ranked by
  total hours added, not by raise count, because a single 40-hour raise is a
  bigger conversation than five 1-hour ones, and DEVIN_PLAN's "magnitude" is
  read as the actual quantity at stake, not an event count.

- **Card 3 (`_staging_card`) ranks by `resolutions` (times declared done),
  filtered to tickets resolved more than once**, rather than by `reopens` or
  by `hidden_rework` alone. A ticket resolved 3 times with 2 reopens is a
  bigger round-trip than one resolved twice with 1 reopen, and `resolutions`
  is the one column that captures magnitude without conflating "still
  bouncing" (`hidden_rework=True`) with "bounced once, long since settled"
  — the row's own `hidden_rework` flag is still shown per row so a reader
  can tell which is which.

- **Card 4 (`_review_card`) combines two different signals in one card,
  each with its own top-3, because DEVIN_PLAN WP6 names them as one line
  item ("Review pairs & self-merges").** Self-merges without outside
  approval (`pr_quality.self_merge`, ranked by
  `merged_without_outside_approval`) and closed review loops
  (`pr_quality.reciprocity`'s `by_person`, ranked by `concentration`,
  restricted to reviewers with `top_partner` set and at least 3 reviews
  given so a single-review "100% concentration" doesn't crowd out real
  patterns) are structurally different failure modes with different
  evidence shapes (a PR list vs. a partner name and a share), so they are
  two separate top-3 lists inside one card rather than forced into one
  ranking with a made-up combined score.
  - `reciprocity`'s input pool is `merged_prs` and `open_prs` concatenated
    (whichever are non-empty) — reciprocity reads `reviews`, which both
    fetch shapes carry, unlike `unprompted_reviews`, which needs the
    extended `timeline_events` payload this page does not require.

- **Evidence links, not evidence text.** Every card builds its own linked
  HTML (`_linked_jira_keys`, `_linked_pr_urls`) directly from the
  underlying frames' `key`/`url` columns, rather than reusing
  `integrity._evidence()`'s formatted strings — `_evidence()` is designed
  for a flag's own summary text and deliberately carries no markup, per its
  own docstring ("a flag's paper trail" as plain text). `_linked_jira_keys`
  uses `render_shared._jira_ticket_url` (the same function every other page
  uses for a ticket link) so a reader clicking any evidence link lands on
  the real ticket, on the real Jira site the rest of the dashboard reads
  from — `test_linked_jira_keys_use_the_real_browse_base_and_the_exact_key`
  checks the URL is well-formed, absolute, and ends in the exact key.
  `_linked_pr_urls` mirrors `pages/code.py`'s own `_pr_evidence_html`
  convention (`#<number>` as the visible label, last URL path segment) for
  a PR link, rather than inventing a second style for the same kind of link
  on a different page.

## Framing rules

- **`theme_html.innocent()` is called exactly once per card, unconditionally
  — including on the empty branch.** Every one of the five `_wrap_card`
  callers (four detail cards plus the roll-up) appends
  `theme_html.innocent(...)` inside `_wrap_card` itself, so there is no code
  path through any card that skips it; `test_every_card_renders_the_
  innocent_reading_even_when_populated` and the four `..._states_its_
  innocent_reading_when_there_is_nothing_to_show` tests both directions.

- **`_top_n` ranks, it does not filter.** DEVIN_PLAN §4.4's "no fixed
  threshold" is implemented as one small function
  (`_top_n(frame, by, n=3)`) used by all four cards' magnitude selection —
  it always returns up to `n` rows, sorted descending, with no comparison
  against any constant. `test_top_n_never_selects_by_a_fixed_cutoff` builds
  five candidates that would all read as "small" under any plausible fixed
  line and confirms exactly three still render, because ranking, not
  filtering, is what decides.
