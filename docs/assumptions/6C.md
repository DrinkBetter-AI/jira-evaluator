# Task 6C — Clockify: billed vs delivered (WP11): assumptions

One bullet per ambiguous call. `clockify.py`'s own module and function
docstrings carry the detailed reasoning; this file is the index of decisions.

## Decisions

- **No Clockify API key or workspace id exists or will exist during this
  task.** `clockify.py` is built and tested entirely against fixture payloads
  written to look like a real detailed-report response
  (`{"timeentries": [...]}`, each entry carrying `id`/`userId`/`userEmail`/
  `userName`/`timeInterval`). No code path has ever made a real HTTP request
  to `reports.api.clockify.me`. `weekly_billed_hours` and `fetch_time_entries`
  are covered for: no key, no workspace, key-without-workspace,
  workspace-without-key, and a fetcher that raises - every one degrades to
  `available=False` with a reason, never a raise, never a zero standing in
  for "we don't know."

- **Created-at tell: verified absent from the API, not implemented, and
  explicitly tested as absent.** Checked Clockify's own API reference
  (docs.clockify.me) and a second independent source describing the same
  `TimeEntry` schema before writing anything. The detailed-report time entry
  object exposes `id`, `description`, `timeInterval`
  (`start`/`end`/`duration`/timezone fields), `project`, `task`, `tags`,
  `billable`, `hourlyRate`, `costRate`, `customFieldValues`, `type`,
  `approvalRequestId`. No field on either source records when the entry
  *record* was written, separate from the work's claimed start/end. Per the
  task instructions, this was not faked from a proxy (entry id ordering, page
  position, or anything else that merely correlates with insertion order).
  `late_created_tell` is implemented as a stub with the same `TellResult`
  shape as the other three detectors, always returning `available=False` and
  the reason inline, and `test_created_at_tell_is_explicitly_absent_not_faked`
  pins both the stub's return value and the fact that the module's own
  entries frame (built straight from the documented response fields) never
  carries a `created_at`/`createdAt` column to begin with.

- **Enforcement stated ahead of detection, in the module docstring itself,
  not just in this file.** Clockify's "Force timer" workspace setting
  (confirmed via clockify.me/help: disables manual entry, only a running
  timer is accepted) is a Pro/Enterprise-plan feature. If the workspace is on
  that tier, turning it on is a stronger fix than anything this module can
  detect after the fact, and is worth doing regardless of whether the
  dashboard ships this page. The three implemented detectors
  (`detect_round_block_weeks`, `detect_one_block_days`, `detect_overlaps`)
  are the fallback for while that setting is off, not a replacement for it.

- **Person mapping is a new, module-owned env var (`CLOCKIFY_USER_MAP`),
  same shape as the others.** `"Jira Name=clockifyEmailOrUserId;..."`,
  parsed the same way `roles.py`'s four env vars are, for the same reason
  6A's `SLACK_USER_MAP` gives: I don't own `roles.py`, and Clockify user
  identity is a fourth namespace this codebase has never carried before.
  Unlike `roles_template.env`'s four vars, `CLOCKIFY_USER_MAP` ships with
  **no baked-in default** - nobody has confirmed a single real Clockify email
  or user id (`DEVIN_PLAN.md` WP11 lists "whether Clockify user emails match
  the vinovoss.com convention" as an open, unanswered prerequisite from
  Angel). Guessing at `name@vinovoss.com` and baking it in risks silently
  crediting the wrong person's hours the day a real key is wired up; every
  active person renders `"unmapped"` until someone who can see the Clockify
  admin panel populates real identifiers.

- **Three-state person status, not two.** `resolve_person_status` returns
  `"mapped"` / `"unmapped"` / `"not_on_clockify"`. `"not_on_clockify"` is
  hard-coded to Praveen Rai (`ROSTER.md`, confirmed by Angel: "the only
  person not on Clockify") and takes priority over an entry in
  `CLOCKIFY_USER_MAP` even if one were mistakenly added for him - the roster
  fact wins, so a data-entry accident can't quietly reclassify the one
  legitimately-absent person as a mapping bug. Every other roster name
  missing from the map is `"unmapped"`, which is a broken-mapping state,
  never `0` and never silently dropped from the output.

- **A "mapped" person's week with genuinely no Clockify entries is a real
  `0.0`, not `NA`.** The task's "never zero" rule is about *unmapped* people
  reading as if they billed nothing; it is not a rule against a verified,
  mapped person having an honest zero-hour week (they were on leave, they
  didn't bill that project that week, whatever). The distinction is carried
  entirely by the `status` column - a renderer that ever collapses
  `"unmapped"` hours to `0` for a chart axis is making the exact mistake this
  task exists to prevent; `status` has to gate the render, not just be
  decoration next to it. Tested directly
  (`test_mapped_person_gets_real_hours_including_a_true_zero_week`).

- **Two separate MAD comparisons, not one, matching "against the person's
  own history and against their role cohort" literally.**
  `self_history_outliers` compares a person-week only to that same person's
  other weeks (needs 3+ of their own weeks to score, same "unanswerable, not
  clean" convention `estimate_accuracy._modified_z` uses). `cohort_outliers`
  compares a person-week only to other mapped people in the same role that
  same week (needs a role lookup hit; `roles.py`'s cohort-folding decisions -
  e.g. frontend/frontend-mobile/mobile sharing one cohort - are a caller
  concern, since `cohort_outliers` takes `role_of` as a plain mapping or
  callable rather than importing `roles.load_roster` itself). Both use the
  same `_modified_z` algorithm and the same `OUTLIER_Z` threshold (imported
  from `estimate_accuracy.py`, not re-declared, so the two files can't
  quietly disagree on where "far enough" sits).

- **`_modified_z` is a documented hand-copy of `estimate_accuracy._modified_z`,
  not an import.** That function is private (leading underscore) to its own
  module and this task does not own `estimate_accuracy.py`. Copying a small,
  well-tested, already-reviewed algorithm with a comment pointing at the
  original is the same tradeoff `roles.CODE_RUBRIC` already makes against
  `kpi.WEIGHTS` in this codebase (also a documented hand-copy, also
  cross-checked by a public constant rather than a private import).

- **Overlap detection uses a running-maximum sweep, not just adjacent pairs.**
  Sorting each person's entries by start time and comparing only consecutive
  pairs misses a nested overlap (entry B entirely inside entry A, with a
  non-overlapping entry C between them in start order). The running-max
  approach (track the latest `end` seen so far; a new entry whose `start` is
  before that running max overlaps whichever earlier entry set the max) has
  no such blind spot for a single person's entries and stays the evidence
  pair - the two entry ids and their times - never a bare count.

## Render/wiring call sites for a later phase

- **The seam WP11 asks for: `estimate_accuracy.hours_per_delivered_line`'s
  hours source.** That function (line ~288, the `logged_hours` column built
  at line ~352 of `estimate_accuracy.py`) currently computes
  `logged_hours = _numeric(frame, "time_spent_sec") / 3600.0` - Jira
  worklogs. `clockify.billed_hours_by_person(weekly)` returns a
  `person -> total mapped hours` `pd.Series` built from
  `weekly_billed_hours(...)`'s output, excluding unmapped and
  not-on-Clockify rows by construction. Once a real Clockify key exists, the
  intended one-line change in `estimate_accuracy.py` (not made here - that
  file is not in this task's file list) is: build `weekly` via
  `clockify.weekly_billed_hours(roster_names, window_start, window_end)`,
  call `clockify.billed_hours_by_person(weekly)`, and reindex that series by
  `frame["assignee"]` in place of the `_numeric(frame, "time_spent_sec") /
  3600.0` expression on that line. Line-level (per-ticket) Clockify
  attribution isn't possible without entries tying a billed hour to a
  specific Jira key, which Clockify's detailed report does not provide
  unless someone adopts a description convention for it - out of scope here
  and not assumed.

- **The three-number Integrity-page triplet** (hours billed / delivered /
  hours logged in Jira, per person per week) is assembled by a future page
  module from three independent calls this task makes possible:
  `clockify.weekly_billed_hours(...)` for the Clockify leg,
  `pr_quality.delivered_points(...)` (already built, aggregate not weekly -
  a later phase would need a weekly variant, not built here) for the
  delivered leg, and Jira `time_spent_sec` bucketed by week for the Jira leg.
  No page or rendering code was added in this task - `clockify.py`,
  `tests/test_clockify.py`, and this file are the only files touched, per
  the file-ownership rule.

- **Angel-only page access** (`ROSTER.md`: "Integrity-page access: decided -
  Angel only") is an `access_gate.py` / page-wiring concern, not a
  `clockify.py` concern - this module has no awareness of who is logged in
  and returns the same result regardless of caller. Flagged here so whoever
  wires this into a page doesn't skip it.
