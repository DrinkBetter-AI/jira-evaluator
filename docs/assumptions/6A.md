# Task 6A — Slack snippet compliance (WP9): assumptions

- **No Slack bot token exists or will exist during this task.** `snippets.py`
  is built and tested entirely against recorded fixture payloads shaped like
  real `conversations.history` / `conversations.replies` responses; no code
  path in this module has ever made a real HTTP request to Slack.

- **Third identity namespace, new env var, owned entirely by `snippets.py`.**
  Slack user IDs appear nowhere else in this codebase and I don't own
  `roles.py`, so the join can't live there. Added `SLACK_USER_MAP`
  (`"Jira Name=SlackUserId;..."`, same shape as `GITHUB_LOGIN_MAP`), parsed by
  `snippets.load_slack_user_map` and resolved against `roles.load_roster()`
  by name inside `snippets.build_report`.

- **`SLACK_USER_MAP` ships with no baked-in default**, unlike `roles.py`'s
  four env vars. Nobody has ever confirmed a real Slack user ID for anyone on
  the roster (no token has ever existed to look one up). Guessing IDs and
  baking them in risks silently crediting one person's snippet to another the
  day a real token is finally wired up. Every Slack author is `unmapped`
  until someone with Slack admin access populates real IDs.

- **"Weekly posting streak" is ambiguous** between "total weeks posted within
  the window" (what the baseline numbers in DEVIN_PLAN.md actually are — e.g.
  Tam 7/8) and "longest/most-recent consecutive run." Implemented both:
  `PersonSnippetStats.weeks_posted` (the total, what the People page's "x/8"
  should render) and `.current_streak` (consecutive weeks ending at the most
  recent week in the window — the literal "streak" reading, for whoever wants
  it later).

- **Week bucketing is ISO week (Monday–Sunday), on the message timestamp,
  UTC.** UTC is the one neutral timezone across the team's Vietnam / Uruguay /
  Tunisia / EU spread, and it's what `cost_client.py` already buckets by.
  Verified this reproduces DEVIN_PLAN.md's "W25–W32" labels exactly against
  the 2026 ISO calendar (`recent_full_weeks(date(2026, 8, 12), 8) ==
  ("2026-W25", ..., "2026-W32")`).

- **"Last 8 full weeks" excludes the in-progress week.** `recent_full_weeks`
  returns the 8 ISO weeks immediately before the week containing `now`, never
  including it — a week in progress would otherwise read as a false "0" for
  someone who simply hasn't posted yet this week.

- **A message counts if it has a `user` field and no `subtype`.** This
  excludes channel-join notices, bot messages, and edited-message system
  entries — the same "don't attribute bot/system noise to a person" instinct
  `roles_template.env` already applies to GitHub bot logins.

- **Rate-limit handling stops and reports, it does not retry.** On HTTP 429
  (or any other pagination failure), `_paginate` returns whatever it already
  collected, flagged `partial` with a reason. Unlike `github_client.py`'s
  shared-budget retry-with-backoff, this module does not wait out Slack's
  `Retry-After` — Slack's can run to a minute, and nothing here has a
  render loop depending on that wait completing the way the GitHub-backed
  pages do. A caller that wants a complete read after a 429 just re-runs
  `weekly_snippet_report`; the partial result already returned is still
  valid data for the weeks it did reach, never silently discarded.

- **Thread replies only fetched for messages Slack itself flags as thread
  roots** (`reply_count` present on the top-level message from
  `conversations.history`). `conversations.replies` re-sends the parent
  message as the first element of its response; it's filtered out by
  matching `ts == thread_ts` so it's never counted twice (once as top-level,
  once as a reply).

- **`SnippetReport.roster_size` counts every active roster person**, mapped
  to a Slack ID or not — an active person with no `SLACK_USER_MAP` entry who
  does post still shows up only in `unmapped`, and the denominator doesn't
  shrink to compensate. Stated as the metric's own blind spot in the
  `SnippetReport` docstring: an unmapped active person always reads as a
  non-poster this week even on a week they posted. That's an admin task
  (finish populating `SLACK_USER_MAP`), not something the metric should paper
  over by quietly excluding them from the denominator.

- **Baseline fixture in `tests/test_snippets.py` also exercises three other
  acceptance behaviours** (three-posts-in-one-week, thread-reply isolation,
  unmapped-author, out-of-window exclusion) rather than only reproducing the
  raw counts, on the theory that one internally-consistent fixture that
  survives several independent assertions is stronger evidence than the
  counts alone.
