# Task 2B assumptions — per-person aggregation (`people_table.py`)

One bullet per ambiguous call, what was chosen, and why.

- **Signature: five bulk frames, not a per-person JQL loop.** The existing
  single-person scorecard (`render_shared._render_scorecard`) fetches
  `resolved_7`/`resolved_30`/`resolved_90`/`reopened_90` with four live JQL
  calls per person. Doing that for a full people table would be N times the
  Jira load for a page whose whole point is "see everyone at once." Instead
  `people_table(open_tickets, resolved_tickets, gradable_tickets, prs,
  events, *, roster=None, resolved_statuses=None, now=None)` takes the same
  bulk frames the rest of the dashboard already fetches once (all people's
  open tickets, all people's recently-resolved tickets, all people's
  quality-scored tickets, all PRs, one `changelog_events` result) and does
  every per-person split itself. This is "wiring, not analysis" read
  literally: no new Jira/GitHub calls, no new field derivations.

- **`resolved_7`/`resolved_90` come from `integrity.credited_resolutions`,
  not a JQL resolved-count.** `kpi.components` takes these as plain ints
  and doesn't care where they came from. The task brief and
  `KPI_SPEC.md` §1 both rank machine-recorded facts over declared ones, and
  `credited_resolutions` is the changelog-author fix for the exact bug
  `docs/assumptions/2A.md` names ("194 resolved, second highest in the
  company" credited to a departed tester's stale assignee field). Using it
  here means the People page's `score` and the credit-fix conversation are
  the same number, not two competing counts.

- **`reopened_90` comes from `integrity_flags`'s `reresolved_tickets` per
  person, not a JQL reopened-count.** Same reasoning: a ticket resolved
  more than once and sitting resolved today is the machine-recorded version
  of "came back," and it is what `events` can actually see. It is not
  identical to Jira's `status CHANGED FROM (resolved) TO NOT resolved`
  reading (a ticket reopened and never re-resolved is invisible to *this*
  count, since `integrity_flags` only counts tickets that came back and
  currently sit resolved) — documented on `_flags_by_person`, not silently
  swapped for an equivalent claim.

- **Identity is the Jira display name; PR-side raw keys (GitHub logins) are
  canonicalized through it.** Tickets and the changelog carry a person's
  Jira name; PR authors and reviewers carry a GitHub login.
  `roles.Roster.name_for_login` is the only thing in this codebase that
  knows both, so every raw key this module reads goes through
  `_canonical_person`, which tries a Jira-name match first, then a login
  match, and falls back to the raw string unchanged (its own identity) when
  neither resolves. A PR author missing from `GITHUB_LOGIN_MAP` therefore
  still gets a row — keyed by their login, `role=None`,
  `no_score_reason="role unknown"` — rather than being merged into
  "Unknown" or silently dropped. `docs/assumptions/2C.md`'s own note on
  `roles.py` (`unmapped_logins`) is the same category of gap; this module
  makes it visible as a row instead of losing it in a groupby.

- **The person universe is "who appears in the data," not "everyone on the
  roster."** An earlier draft unioned in every active roster name so a
  silent contractor with zero tickets, zero PRs and zero changelog activity
  would still get a row (arguably the more useful behaviour for a manager
  auditing ghosts). Dropped it: `roles.load_roster()`'s baked default
  carries ~20 real names, so "call with five empty frames" would still
  return ~20 rows, which fails the acceptance test's plain reading of
  "empty in, empty out." A person only appears here if their name/login
  shows up as a ticket assignee, a changelog author, or a PR author -
  which is also how `docs/assumptions/2A.md`'s "Former staff never appear"
  requirement composes cleanly: filter is `roster.is_active(person) is not
  False` after the union, so a departed employee is dropped regardless of
  which source surfaced their name, and someone not on the roster at all
  (`is_active` returns `None`) is kept, not dropped.

- **`score`/`n`/`measurable_pct`/`no_score_reason` go through exactly two
  paths, chosen by `roles.rubric_for_person`.** Code-producing roles
  (`roles.CODE_ROLES`) use `kpi.components` -> `kpi.overall` /
  `kpi.coverage`, identical to the single-person scorecard. Every other
  outcome - a rubric that exists but has no component-computation wired yet
  (QA/PM/design/infra, per `docs/assumptions/2C.md`: "future work, not this
  task's job"), no rubric at all (seo/wine/advisor), exec, or not on the
  roster - goes through `roles.overall(person, roster,
  component_scores={})`. Calling it with an empty map is not a workaround;
  it is precisely what that function is for, and it already returns the
  right sentinel for all four cases (`EXEC_REASON`, the no-rubric string,
  `"role unknown"`, or "not scored: only 0 of N points... had data") without
  this module special-casing any of them. `measurable_pct` for that second
  path is `0.0`, not `NaN`: there is no rubric with computed components to
  report a percentage of, and the acceptance criterion is that the column
  is never null, not that a rubric-less role gets a fabricated positive
  number.

- **`score`'s own `n` is the sum of `Component.n` over the components that
  actually had data**, not a ticket/PR count invented separately. Every
  `kpi.Component` already carries its own sample size; summing the
  sufficient ones is the honest "how much evidence stands behind this
  number" figure and costs nothing extra to compute. For the
  `roles.overall`-only path, `n=0` — no components are computed yet for
  those rubrics, so zero is the correct count, not a placeholder.

- **`n_ttfr_hours` is `prs_reviewed`, an upper bound, not the exact count.**
  `pr_quality.review_citizenship` computes the narrower "PRs where this
  person was first" count internally (via its private `first` frame) but
  does not return it, and this module does not reach into
  `pr_quality._review_events` to get it — that would mean depending on a
  private name in a file this task does not own. Documented as an
  approximation on `_review_lookup`'s docstring rather than worked around.

- **`n_delivered_points` counts every PR the author has (including
  unsized ones); `n_trivial_share` counts only sized PRs.**
  `pr_quality.DeliveredPoints.prs` is the raw per-author PR count from
  `size_bands`, including PRs whose diff size the API never returned (they
  earn 0 points but are still real PRs); `trivial_share`'s own denominator
  is explicitly "share of *sized* PRs" per `pr_quality.size_bands`'s
  docstring. The two `n`s are therefore genuinely different denominators
  for the same author, both correct for what they measure — not an
  inconsistency to be resolved.

- **`flag_severity` is a new number, not one that exists anywhere in
  `integrity.py`.** `integrity_flags` deliberately returns four booleans
  and no combined score ("a single number would be argued with"). The
  brief for this table asks for a `flag_count`/`flag_severity` pair, so
  `flag_severity` had to be invented here: `FLAG_SEVERITY_WEIGHTS` scores
  `staging_pingpong` and `rework_hidden` (both mint resolution credit
  nothing else on the scorecard can see) at 3.0, `estimate_inflation`
  (moves billed hours directly) at 2.0, and `board_grooming` (the flag with
  the most innocent reading - a lead who actually grooms the backlog looks
  identical) at 1.0. `flag_severity` is the sum of tripped flags' weights,
  and it shares `n_flag_count`'s value as `n_flag_severity` - both are
  read off the same four booleans and the same window of changelog
  activity, so a second, independently-computed `n` would just be a copy.

- **`flag_count`/`flag_severity` default to a real `0`/`0.0` when the
  events pipeline ran but a person tripped nothing; they are `NA` only
  when there was no changelog at all.** `integrity_flags`'s own docstring
  says this directly: "an empty row is not a clean bill of health: someone
  who does nothing at all trips nothing at all." Applied literally: if
  `events` is non-empty overall (the pipeline produced real output) but a
  specific person's canonical name never appears in `integrity_flags`'s
  result, that is a known, reportable zero. If `events` itself is
  empty/missing, nothing about anyone's flags is knowable, and the value is
  `pd.NA`. `reviews_given` and `delivered_points` follow the same rule
  against `prs`'s emptiness (a fetched-but-empty PR history for one person
  inside a non-empty team fetch is a real zero PRs, not missing data);
  `cycle_median`, `ttfr_hours`, `estimate_ratio`, `estimate_iqr` and
  `trivial_share` are always `NA` when absent, because "zero cycle days"
  or "zero estimate ratio" is not a coherent claim the way "zero PRs
  authored" is.

- **`all_tickets` for `integrity.cycle_time` / `integrity_flags` /
  `estimate_accuracy.accuracy_by_person` is `open_tickets` concatenated
  with `resolved_tickets`, column-aligned by `pd.concat(..., sort=False)`.**
  All three functions read a mix of currently-open and resolved-state
  fields (`cycle_time` wants `created`/`assignee` regardless of status;
  `integrity_flags` passes `tickets` straight through to
  `reresolve_events`, which wants live `status` to resolve
  `currently_resolved`; `accuracy_by_person` filters to done tickets
  itself via `estimate_accuracy.is_done`). Handing each function the union
  once, rather than asking the caller for a third "all tickets" frame, is
  the join this module exists to do.

- **`estimate_accuracy.accuracy_by_person` is called exactly once, on
  `all_tickets`**, not per person. It already groups by `assignee`
  internally; calling it once and indexing the result is both cheaper and
  the reason `test_estimate_accuracy_is_actually_called_...` can assert a
  call count without asserting an exact number of calls (`>= 1`, since a
  future refactor that widens this to more windows would still be honest
  wiring, not a regression).

- **Peer pool for the code rubric's "Delivery vs team" component is the
  person's `roles.peer_cohort`, not the whole team.** `kpi.peer_percentile`
  only needs `MIN_PEERS` (3) numeric values and doesn't care who they
  belong to, but comparing an engineer against PMs and designers would be
  the wrong "team" - `roles.peer_cohort` (built in 2C specifically for
  this) already knows the fold rule (frontend/frontend-mobile/mobile share
  one cohort) and the sufficiency floor. A cohort peer absent from the
  `resolved_7` dict is scored `0`, not dropped: once `events` is
  non-empty, "not in the credited-resolutions table this week" is a real
  zero for that peer, and dropping them would shrink the cohort below
  `MIN_PEERS` for no honest reason.

- **`resolved_statuses` and `now` pass straight through to every
  `integrity.py` call that accepts them; `estimate_accuracy.py` gets
  neither (it has no notion of "now").** No new default is invented here -
  omitting `now` uses the real current time, same as every other caller of
  these functions in the codebase; tests pin it exactly the way
  `tests/test_integrity.py` already does.

- **Nothing in `people_table.py` calls `pr_quality.unprompted_reviews`,
  `roles.rubric_for` (the `kpi.py` alias), `series.py`, or
  `ticket_quality.score_tickets`.** The task's required column list
  (`person · role · score · n · delivered_points · trivial_share ·
  cycle_median · reviews_given · ttfr_hours · estimate_ratio ·
  estimate_iqr · flag_count · flag_severity · measurable_pct ·
  no_score_reason`) does not include an unprompted-reviews column, and
  `gradable_tickets` is documented as arriving pre-scored
  (`ticket_quality.score_tickets`'s output), matching how
  `render_shared._render_scorecard` already builds it - computing quality
  scores is not in this task's "files you own" list.
  `pr_quality.unprompted_reviews` (2D's proactivity signal) is real,
  useful, and explicitly out of this table's frozen schema; wiring it in
  is a natural follow-up column, not silently done here under a different
  name.

## Public API (for the People page agent to code against)

```python
COLUMNS: list[str]  # the exact 24 column names, in order (see below)

def people_table(
    open_tickets: pd.DataFrame,
    resolved_tickets: pd.DataFrame,
    gradable_tickets: pd.DataFrame,
    prs: pd.DataFrame,
    events: pd.DataFrame,
    *,
    roster: roles.Roster | None = None,
    resolved_statuses: Iterable[str] | None = None,
    now: object | None = None,
) -> pd.DataFrame: ...
```

One row per person. Column order and dtype:

| column | dtype | notes |
|---|---|---|
| `person` | `object` (str) | canonical identity — Jira display name, or a raw GitHub login when unmapped |
| `role` | `object` (str or `None`) | from `roles.Roster.role_of`; `None` when not on the roster |
| `score` | `Float64` | `None`/`NA` below the rubric's measurable-weight floor, for exec, for a no-rubric role, or for an unclassified role — **never `0`** |
| `n` | `Int64` | sample size backing `score`; `0` for every non-code-rubric path |
| `delivered_points` | `Float64` | size-weighted PR output (`pr_quality.delivered_points`); `NA` only when `prs` itself is empty |
| `n_delivered_points` | `Int64` | total PRs authored, sized or not |
| `trivial_share` | `Float64` | share of *sized* PRs that were trivial; `NA` with zero sized PRs |
| `n_trivial_share` | `Int64` | sized PR count |
| `cycle_median` | `Float64` | median lead time in days (`integrity.cycle_time`) |
| `n_cycle_median` | `Int64` | tickets with a computable lead time |
| `reviews_given` | `Int64` | `pr_quality.review_citizenship`; `NA` only when `prs` itself is empty |
| `n_reviews_given` | `Int64` | distinct PRs reviewed |
| `ttfr_hours` | `Float64` | median hours to first review, only counting PRs where this person was first |
| `n_ttfr_hours` | `Int64` | **upper bound** — `prs_reviewed`, not the narrower "was first" count (see assumptions above) |
| `estimate_ratio` | `Float64` | median logged/estimated hours (`estimate_accuracy.accuracy_by_person`) |
| `n_estimate_ratio` | `Int64` | tickets with both an estimate and logged time |
| `estimate_iqr` | `Float64` | interquartile range of the same ratio distribution |
| `n_estimate_iqr` | `Int64` | same ticket count as `n_estimate_ratio` |
| `flag_count` | `Int64` | 0–4, `integrity.integrity_flags`; real `0` once `events` is non-empty |
| `n_flag_count` | `Int64` | total signal-event count the four flags were computed from |
| `flag_severity` | `Float64` | weighted sum of tripped flags (`FLAG_SEVERITY_WEIGHTS`); shares `n_flag_count`'s value |
| `n_flag_severity` | `Int64` | identical to `n_flag_count` |
| `measurable_pct` | `Float64` | **never null**, on every row |
| `no_score_reason` | `object` (str) | `""` when `score` is not null; otherwise the specific reason |
