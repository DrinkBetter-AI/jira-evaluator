# Task 2D assumptions

One bullet per ambiguous call, what was chosen, and why.

- **The "extended GraphQL" wasn't actually written yet.** The task brief says
  it "is already written in `github_client.py` and are not enabled." What
  exists is the *detail* payload's own `timelineItems` (READY_FOR_REVIEW_EVENT
  + REVIEW_REQUESTED_EVENT, `createdAt` only, no reviewer) - enough for
  `review_ready_at` and nothing else. Neither `draft_transitions` (needs
  `ConvertToDraftEvent`) nor `unprompted_reviews` (needs the reviewer on each
  `ReviewRequestedEvent`) can be built from it. Wrote the actual extended
  query: a second, aliased `timelineItems` field
  (`draftRequestTimeline`, `github_client.py` ~L360-400) carrying all three
  event types plus `requestedReviewer{login}` on the request event, added to
  the detail payload rather than replacing it, so `review_ready_at` keeps
  using the cheap field it always has.

- **New functions, not new parameters on the existing ones.** `fetch_open_prs`
  and `fetch_merged_prs` are called today from `data_layer.py` (owned by
  another agent) with fixed positional/keyword shapes and a `DataFrame`
  return type the whole rest of the app depends on. The task wants the
  degraded state "exposed as a value the page can render" - a `degraded: bool`
  + `reason` - which cannot be bolted onto a function that must keep
  returning a bare `DataFrame`. Added `fetch_open_prs_extended` /
  `fetch_merged_prs_extended`, returning a new `PRFetch` NamedTuple
  (`frame`, `degraded`, `reason`), as separate opt-in functions. Nothing that
  already calls `fetch_open_prs`/`fetch_merged_prs` changes behaviour; the
  extended functions have zero callers until Phase 3 wires them in (see
  below).

- **The switch is an env var, `GITHUB_EXTENDED_PR_DATA`**, read via
  `github_client.extended_pr_data_enabled()`, off by default - consistent
  with the file's existing `GITHUB_ORG` / `GITHUB_EXCLUDE_REPOS` pattern.
  When off, `fetch_*_extended` return `degraded=True` with a "switched off"
  reason rather than silently doing nothing, so a caller cannot forget to
  check the flag and misread empty draft/unprompted data as "nobody's
  cheating."

- **On failure, the extended query degrades to the *lean* query, not the
  detail one**, even though the existing detail payload is arguably "safer"
  to fall back to. Chose lean because the extended query's failure mode is
  most often a throttled token (that's the whole reason the module retries at
  all) - if the token can't afford the extended read, it may not be able to
  afford the detail read either, and asking for detail *as the fallback for a
  throttle* would burn more of the same budget that just got refused. This
  matches the task text literally ("degrade to the lean query") and the
  existing `_search_prs` precedent (detail degrades to lean, not to nothing).
  If even the lean fallback fails, that's a real outage: `PRFetch` still
  never raises - it returns an empty frame with `degraded=True` and an
  "unavailable" reason.

- **Caching lives inside `github_client.py`, not in a `st.cache_data`
  decorator**, because `data_layer.py` (unowned) already wraps
  `fetch_open_prs`/`fetch_merged_prs` at `ttl=300` (5 minutes) - fine for the
  ~29-1,030 point lean/detail reads, ruinous for the extended one (~several
  times the detail cost) reused every five minutes. Built a small
  `time.monotonic()` + lock cache inside the client
  (`_EXTENDED_CACHE`, `_EXTENDED_CACHE_TTL_SECONDS = 3600.0`) so the >=1h
  floor holds regardless of what TTL a future caller wraps it in. Keyed on
  `(kind, org, query, max_prs[, hygiene])`.

- **`requestedReviewer` only resolves `User` and `Bot`.** GitHub's
  `RequestedReviewer` union also includes `Team` and `Mannequin`; a review
  request routed to a team has no single login and is not represented in the
  fixture-level model `pr_quality.unprompted_reviews` reads. A team-requested
  reviewer who then reviews is silently absent from that reviewer's evidence
  rather than guessed at - stated in the function's docstring as part of its
  blind spot, not fixed, since there is no live token in this environment to
  verify a `Team` fragment's exact shape against.

- **`unprompted_reviews` ordering rule: prompted only by a request at or
  before the review's `submitted_at`.** The acceptance criteria is explicit
  that a request arriving *after* the review still counts it unprompted -
  implemented as `any(requested_at <= submitted_at for ...)`; a request
  logged later never retroactively prompts a review that already happened.
  Pinned by `test_a_review_request_arriving_after_the_review_still_counts_it_unprompted`.

- **`draft_transitions`'s `after_review_request` uses "any draft time after
  any request time,"** not "the first draft time after the first request
  time." With one request and one draft conversion these are the same test;
  chose the looser `any`/`any` because a PR can be re-requested and
  re-drafted multiple times, and the task's framing ("went draft *after* a
  review was requested") is about whether the ordering ever happened, not
  about the first occurrence specifically. A PR that goes draft, comes back,
  gets asked for review again, and goes to draft a second time is exactly the
  exploit-6 pattern and should flag regardless of which round trip triggered
  it.

- **`delivered_points` returns `list[DeliveredPoints]`, not a `DataFrame`.**
  A `DataFrame` would let a caller write `out["prs"]` and hand around a bare
  count series - exactly the shortcut KPI_SPEC §3.3 rules out ("no `.count`
  shortcut that works without the size"). `DeliveredPoints` is a `NamedTuple`
  with no default on `median_changed_lines`, so constructing one without it
  is a `TypeError` at the call site, not a silently-missing value; there is
  no second, scalar-returning function anywhere in the module.

- **`SIZE_POINTS` weights are invented, not derived** (trivial=1, small=3,
  medium=8, large=20, oversized=20 - flat past `large`, since the band's own
  docstring calls `oversized` "too big to review honestly," which should not
  earn *more* than large for being bigger still). No KPI_SPEC number exists
  for this; documented the reasoning in `SIZE_POINTS`'s own comment so a
  later reader can adjust the constants without re-deriving the intent.

- **Real call sites given to `reciprocity`, `abandoned_rate`, `size_bands`
  from inside the new functions, not decoratively:**
  - `delivered_points` is built directly on `size_bands` (classifies once;
    the two functions cannot disagree about which band a PR is in).
  - `draft_transitions.outcome` runs `abandoned_rate` on exactly the subset
    of PRs flagged `after_review_request`, answering "of the PRs that hid in
    draft after being asked for review, how many actually shipped" with the
    real abandoned-work arithmetic instead of inventing a second one.
  - `unprompted_reviews` joins `reciprocity`'s `by_person` frame
    (`top_partner`, `top_partner_share`, `concentration`) onto its own
    per-reviewer result, so a reviewer whose "unprompted" reviews are all
    aimed at one colleague reads as the closed approval loop reciprocity
    already flags, not as proactivity.

## Render call sites for Phase 3

None of these were touched (out of ownership for this task). Listed so the
next agent doesn't have to re-derive them.

- **`data_layer.py` ~L536-548** (`_open_prs_cached`, `_merged_prs_cached` or
  similarly-named wrappers around `github_client.fetch_open_prs` /
  `fetch_merged_prs`, both `@st.cache_data(ttl=300)`): add sibling cached
  functions calling `github_client.fetch_open_prs_extended` /
  `fetch_merged_prs_extended`, unwrapping the returned `PRFetch` into
  `(frame, degraded, reason)` so the 300s Streamlit cache wraps a value that
  is itself already floor-cached at >=1h inside the client - the two caches
  do not conflict, the inner one just makes repeated 300s misses cheap.

- **`pages/code.py`**: the natural home for all three new functions, per
  DEVIN_PLAN WP4's Code page scope (stuck/never-reviewed queues, size bands,
  traceability, review citizenship, abandoned rate - this task's siblings).
  Render `pr_quality.draft_transitions(...).detail` as a queue - specifically
  the PRs where `after_review_request` is true, which is exactly the set
  that `_open_query`'s `draft:false` makes invisible everywhere else on the
  dashboard (KPI_SPEC exploit #6). Render `pr_quality.delivered_points(...)`
  as the size-weighted leaderboard the raw PR-count tile should stop being
  read as. Render the `PRFetch.degraded`/`reason` from the data-layer call
  above as an `st.info` banner at the top of the page ("PR quality data
  unavailable - lean mode" per WP4's own acceptance text) - this is exactly
  the `st.warning`-from-a-compute-module the task says not to do, and
  `pr_quality`/`github_client` deliberately hand back a plain value instead.

- **`pages/people.py`**: `pr_quality.unprompted_reviews(...)` is DEVIN_PLAN
  §6's decided Proactivity panel signal #2 ("PR reviews given unprompted...
  the WP4 data distinguishes these"). Render per-person with the PR numbers
  as the evidence links, next to the other two decided proactivity signals
  (out-of-lane reports, early blockers - neither owned by this task).

- **`render_shared.py`'s stuck / never-reviewed queue builders** (whichever
  helper currently filters the `draft:false` open-PR frame for those two
  today-page/code-page cards): once `fetch_open_prs_extended` exists in the
  data layer, union in `draft_transitions(...).detail` rows flagged
  `after_review_request` so a PR hidden by exploit #6 surfaces in the same
  queue it would have been in had it stayed open and undrafted, instead of
  only in a separate "draft round-trips" card nobody is required to check.
