# Task 1B assumptions

One bullet per ambiguous call, what was chosen, and why. `theme_html.py`'s
own module docstring restates the backward-compatibility mechanism in full;
this file is the reasoning behind it and every other judgment call.

## Backward compatibility: `tiles`/`hbars`/`table`

- **Detection, not a version flag.** `tiles`, `hbars` and `table` each accept
  both the pre-1B shape (plain tuples, writes directly, returns `None`) and
  the new shape (`Tile`/`Bar`/`Column`+`Cell`, returns a string). Which one
  runs is decided from what was actually passed, not from a caller-supplied
  switch:
  - `tiles(cards)` - legacy if `cards` is empty or its first item is not a
    `Tile`.
  - `hbars(bars, *, title=...)` - legacy if `title` was passed (the old
    signature required it as a keyword) or `bars` is empty or its first item
    is not a `Bar`.
  - `table(columns, rows, ...)` - legacy if the first argument is a
    `pandas.DataFrame` (the old call shape was `table(frame, columns, *,
    title=...)`).
  Every one of the three also takes an explicit `write: bool | None = None`
  that overrides the auto-detection outright, satisfying the task's
  "write=True-style path" ask directly rather than through a second set of
  `*_write` wrapper functions - one flag, three functions, same idea.
- **The old code paths are untouched, not reimplemented.** Rather than build
  one unified renderer and try to make it produce byte-identical output to
  the pre-1B version for the legacy shape, the original function bodies were
  kept verbatim (renamed `_legacy_tile_html`, `_legacy_hbars_html`,
  `_legacy_table_html`). This is the lower-risk choice: the four existing
  tests in `tests/test_theme_html.py` (escaping, bar-width proportionality,
  severity colouring, empty-table rendering) assert on the exact HTML those
  functions produce, and rewriting the logic to flow through the new
  `Tile`/`Bar`/`Cell` types risked a silent formatting drift those tests
  would not catch (e.g. a decimal place, a class name order).
- **Phase 3 should use the new, returning form** - build fragments with
  `tiles()`/`hbars()`/`table()`/etc., hand them all to `render()` once per
  section. The legacy shape exists only so `pages/code.py` and
  `pages/delivery.py`, which predate this file's API and are out of 1B's file
  ownership, keep working unmodified.

## Card composition is not part of the kit

- The contract lists `hbars(bars) -> str` and `table(columns, rows) -> str`
  with no `title`/`subtitle`/`footer` parameters, unlike their legacy
  counterparts. Read literally: the new forms return only the bare
  `.hbars`/`<table>` fragment, and the surrounding `.card` +
  `.chart-title`/`.chart-sub` wrapping (which the mockup always draws around
  them) is the caller's to compose, the same way a page would wrap `spark()`
  or `legend()` in whatever container it needs. There is deliberately no
  generic `card()` function in this file - the eighteen functions given are
  the whole surface, and a generic wrapper wasn't one of them.
- The same reasoning applies to `hero()` + `decide_cards()`: the mockup's
  outer `<div class="hero">` grid that lays the lead card and the three
  decide-cards side by side is composed by the page (e.g.
  `render(f'<div class="hero">{hero(...)}{decide_cards(...)}</div>')`), not
  returned by either function alone.

## Tone vocabulary

- `hero`, `decide_cards`, `callout`, `sprint_card`'s accent, and the `Bar`/
  `Cell` `tone` fields all use the same five-value vocabulary:
  `theme_tokens.STATUS`'s four keys (`good`/`warn`/`crit`/`info`) plus
  `"gray"` as a neutral fifth (matching `chip()`'s existing tone set, which
  predates this task). This replaces the old `tiles()`-only vocabulary
  (`danger`/`warning`/`good`/`info`/`neutral`), which is kept solely for the
  legacy tuple shape (`_ACCENT_TEXT`) since that input shape is frozen by the
  existing tests and call sites.
- `_hue_var()` is the single place a tone or a series key (`"s1"`..`"s8"`,
  `"--s1"`, `"good"`, ...) becomes a CSS colour reference. It never resolves
  to a raw hex - every colour drawn by `spark()`, `linechart()`, `hbars()`,
  `scorebar()`, `avatar()`, `chip()` and friends is `var(--token)`, so the
  whole component kit repaints automatically if `theme_tokens.py`'s values
  ever change, and this file never types a hex for a chart colour.

## `Tile.delta_good` vs `Tile.delta_dir`

- The mockup's own CSS carries a warning comment: colour must never be the
  only signal, and specifically must never be tied to direction alone (an
  "up" delta is not always good - PRs opening faster is bad). `Tile` has two
  independent fields: `delta_dir` (`"up"`/`"down"`/`"flat"`) always chooses
  the arrow glyph (▲/▼/—); `delta_good` (`True`/`False`/`None`) always
  chooses the text colour (`good-t`/`crit-t`/none), through `_delta_class()`.
  A caller must set `delta_good` explicitly - there is no default inference
  from `delta_dir`, on purpose, so a page cannot accidentally reproduce the
  up-is-green bug the mockup's comment is warning against.

## `Cell` is one NamedTuple for seven cell kinds

- Rather than a `Cell` subtype per `Column.kind`, `Cell` carries five
  optional fields (`value`, `tone`, `note`, `hue`, `pct`) and each renderer
  reads only the ones its kind needs. This keeps the contract's "define
  `Cell` as a `NamedTuple`" literal (one type, not a union of several), and
  it is why `"chip"`/`"avatar"`/`"scorebar"` cells are safe by construction:
  their renderer calls `chip()`/`avatar()`/`scorebar()` on the Cell's fields,
  which escape internally the same as a `"text"` cell would - only
  `kind="html"` is a verbatim pass-through, and that is stated in `Cell`'s
  and `table()`'s docstrings: server-built fragments only, never Jira/GitHub
  text.

## `sprint_card`'s `window` is plain text

- The mockup's ML sprint card replaces the date-range line with a
  `<span class="chip warn">⚠ no dates set</span>`. `sprint_card`'s `window`
  parameter is typed `str` in the contract with no way to pass a pre-built
  fragment, so that special case is not reproduced inside `sprint_card` - the
  mockup itself handles it as a separate `callout()` card directly beneath
  the three-board grid (`"Blocked on config"`), which is the pattern a page
  should follow rather than smuggling markup through `window`.

## Chrome greys with no `theme_tokens` counterpart

- Three greys the mockup writes as bare literals, never promoted to a
  `--variable`: `#e2e8f0` (`.scorebar .tr`/`.comp .tr` base track),
  `#cbd5e1` (`.hbar.dim .track`), `#f6f8fb` (table header background).
  `theme_tokens.py` cannot be edited under 1B, and none of these three exist
  there today (unlike `MUTED_BG`, which task 1A already extracted). They are
  defined once, locally, in `theme_html.py`'s `_CHROME` dict, with a comment
  pointing at the precedent `MUTED_BG` set in `docs/assumptions/1A.md`: real,
  reused mockup literals that were never declared as tokens, not new
  invented colours. If `theme_tokens.py` ever grows a home for these, this
  dict should be deleted in favour of it.

## Report recording - verdict and fix

- **Verdict: confirmed.** `pages/code.py` and `pages/delivery.py` import
  `theme_html` and `page_shared._download_report`, but never import or call
  `page_shared._tile`/`_kpis`/`_said`. Every KPI tile, ranked-bar chart and
  table on both pages is drawn purely through `theme_html.tiles`/`hbars`/
  `table`, none of which touched `page_shared._report()`'s bookkeeping before
  this task. `_download_report(slot, TAB_ENGINEERING)` therefore builds its
  "Download report" file from whatever `page_shared._report("Engineering")`
  has accumulated - which, for everything Code and Delivery draw, is
  nothing. `pages/engineering.py` and `pages/business.py`, by contrast, call
  `_tile`/`_kpis`/`_said` directly and are recorded correctly today. (Read
  both files to confirm; grep for `_tile(`/`_kpis(`/`_said(` across
  `pages/*.py` shows the split exactly this way.)
- **Why the fix has to live in `theme_html.py`, and why it's partial today.**
  `page_shared.py` already imports `theme_html` (`page_shared.py:73`), so
  `theme_html.py` importing `page_shared` back would be a cycle - not
  attempted. `pages/code.py` and `pages/delivery.py` are out of 1B's file
  ownership, so the one-line change that would actually turn this recording
  on today (passing `tab=`/`section=` at each of their ~7 `theme_html.tiles`/
  `hbars` call sites) is not made here. What *is* done here: `tiles()` and
  `hbars()` both take optional `tab: str | None = None, section: str | None
  = None` keywords. When supplied, they call a small `_record()` helper that
  writes into `st.session_state["tab_reports"]` - the exact same dict
  `page_shared._report()` reads and writes, using the standalone `report`
  module (`report.Report`) both files already depend on, which has zero
  project-internal imports and so creates no cycle. Recording happens
  whenever `tab`/`section` are given, independent of whether the call also
  writes to the page (the legacy branch and the new, `write=True` branch
  both record; the new default - return a string, let `render()` draw it
  later - also records, since the values being recorded are about to be
  shown either way).
- **The one duplicated literal.** `_REPORTS_KEY = "tab_reports"` in
  `theme_html.py` is typed out again rather than imported from
  `page_shared.REPORTS_KEY`, for the same cycle reason. If that key is ever
  renamed in `page_shared.py`, this literal has to move with it or recording
  silently stops merging into the same report - flagged here so whoever
  touches `page_shared.REPORTS_KEY` next finds this.
- **What Phase 3 gets for free.** When `pages/code.py` and
  `pages/delivery.py` are rewritten against the new `Tile`/`Bar` API (as the
  task brief says every future page will be), adding `tab="Engineering",
  section="Code"` (or `"Delivery"`) to each `tiles()`/`hbars()` call is the
  entire fix - one keyword pair per call site, not a second `_tile`/`_kpis`
  call duplicated at each of the ~12 call sites across both files.
- Added `test_a_rendered_tile_set_appears_in_the_report_recorder` and
  `test_hbars_also_records_when_given_a_tab_and_section` in
  `tests/test_theme_html.py` to lock this in; `table()` was deliberately left
  out of recording - `page_shared` has no `_table`-shaped recorder to mirror
  (only `_tile`/`_kpis`, both metric-shaped, and `_said` for notes), so there
  is no existing report-shape for a full table to fit into.

## `scorecard()`'s insufficient-component invariant

- `Component.score` is typed `float | None` and is read only inside
  `scorecard()`'s `if component.sufficient:` branch. The `else` branch never
  touches `component.score` at all - it prints the literal string `"n/a"`
  unconditionally. This means there is no argument combination, including a
  numeric `score` deliberately set on a `sufficient=False` component, that
  reaches the page as a number; the test
  `test_insufficient_component_never_renders_as_a_number` passes `score=999`
  on such a component specifically to prove the number is unreachable, not
  merely unlikely.

## Misc

- `linechart()`'s gridlines round the true data max up to the nearest "nice"
  number (1/2/2.5/5/10 × a power of ten - `_nice_ceiling()`), rather than a
  fixed domain like the mockup's hardcoded `mx=150`. This generalises to
  arbitrary data (the mockup's own chart only ever draws one fixed 12-week
  window) while keeping the same four-gridline, round-number look.
- `linechart()` plots each series against its own point count (mirroring how
  `spark()` already scales one series), rather than requiring every series
  and `x_labels` to share one length. This is what lets "series of differing
  length" not crash: two series with 12 and 9 points both draw correctly,
  just spaced differently along the same width - there is no attempt to
  align point *N* of one series with point *N* of another when their counts
  differ.
- Hover tooltips are native `<title>` children on each `linechart()` point
  circle (`title=` attributes pass through `st.markdown`'s `<script>`-only
  strip). `spark()` has no tooltip - the contract gives it no `aria`/label
  parameter to hang one from, and the mockup's own sparklines have none
  either (only the big line chart does).
