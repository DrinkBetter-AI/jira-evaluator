# Task 2E assumptions

One bullet per ambiguous call, what was chosen, and why.

- **`ghost_assigned()` reconciles against the former-staff list, not an
  enumerated active roster.** "Open tickets whose assignee is not on the
  active roster" is implemented as "open tickets whose assignee matches
  someone on `JIRA_FORMER_STAFF`" - the smaller, already-agreed list -
  rather than by building the active-roster side of that comparison, which
  is `roles.py`'s job (another agent, in progress concurrently in this same
  tree). Parsing is a private ~10-line helper (`planning_metrics._former_staff`)
  reading `JIRA_FORMER_STAFF` from the environment with the 22-name
  `roles_template.env` list baked in as a fallback, deliberately not
  importing `roles.py` so this task's schedule doesn't couple to that one's.
  Consolidate later: once `roles.py` exposes a former-staff accessor,
  `_former_staff()` here can delegate to it instead of parsing the env
  itself.

- **"Open" means `status_category != "Done"`**, used consistently by
  `ghost_assigned`, `no_priority_count`, and `outside_any_sprint_count`.
  This is the same signal the rest of the codebase reaches for
  (`estimate_accuracy.py`, `transformations.py`); there's no repo-wide
  single "is this ticket open" helper to import, so a small private
  `_open_mask()` was written in `planning_metrics.py` rather than depend on
  `render_shared._metrics_df` (owned by another task, and it does something
  different - it drops the Backlog *family* of statuses under a UI toggle,
  not "not Done").

- **`carry_over_per_sprint()` counts tickets, not raw `carry_over_count`
  values.** A ticket with `carry_over_count == 3` contributes `1` to its
  current sprint's "Carried over" tally, not `3` - summing the raw field
  per sprint would both misrepresent "how many tickets rolled over" as "how
  many sprint-roll-over events happened" and produce numbers close enough to
  the existing lifetime-mean component (`hygiene.py:121`, `kpi.py:323`) to
  read as a duplicate of it on the page. Verified explicitly in
  `test_carry_over_per_sprint_counts_tickets_not_the_raw_lifetime_number`.

- **The "excluded from totals, not counted as zero" rule for a dateless
  sprint applies to `capacity.capacity_table_by_sprint` and
  `carry_over_per_sprint`, not to `unestimated_per_sprint` or the two
  board-hygiene bars.** The redesign patch is explicit that this is
  specifically an hours/rollup problem ("Carry-over and utilisation stay
  blank for ML rather than reading zero, because the board has no dates and
  a zero would be a claim the data cannot support") - both of those
  aggregate a *rate* across sprints where a dateless sprint's contribution
  is genuinely unknowable (available hours need `working_days`; the
  lifetime-adjacent carry-over share is meant to read alongside utilisation
  on the same page). A raw ticket count (`unestimated_per_sprint`,
  `no_priority_count`, `outside_any_sprint_count`) does not depend on the
  sprint's calendar window to be correct, so nothing is excluded there -
  `unestimated_per_sprint` still returns the dateless sprint names as its
  second value, purely so the page can label them, but every row and any
  total the caller derives includes them.

- **`unestimated_per_sprint`'s `UNKNOWN` sentinel is the string
  `"unknown"`, not `None`/`NaN`.** `None`/`NaN` survives exactly one
  `pd.to_numeric(..., errors="coerce")` or `.fillna(0)` call before it
  silently becomes `0` - which is the bug this metric exists to prevent. A
  string sentinel coerces to `NaN` (never `0`) under `to_numeric`, and nothing
  in `unestimated_per_sprint` calls `to_numeric`/`fillna` on the `Coverage`
  column, so there is no code path inside this module that could produce
  the collapse. `capacity.py`'s own status columns already use this idiom
  (`UNKNOWN_AVAILABILITY = "Unknown"`), so this matches existing convention
  rather than inventing a new one.

- **`unestimated_per_sprint` only counts `original_estimate_sec`, not a
  text-only original estimate.** `hygiene.estimate_policy` credits a ticket
  with only a human string ("2h", no numeric seconds) as estimated, because
  that function is about *policy compliance*. This metric is a per-sprint
  *hours* view, where a words-only estimate contributes no numeric hours
  either way, so it is treated the same as no estimate. Named as this
  function's blind spot in its own docstring, per `KPI_SPEC.md` §1 rule 3.

- **`capacity_table_by_sprint`'s cross-sprint totals reuse the existing
  `weekly_hours` declaration verbatim per sprint, with no per-board roster
  to filter against.** `capacity_table` already renders an idle roster
  member as a "Has room" row for one sprint, by design ("idle capacity is
  the point of the view"). Extended literally across sprints, a person
  declared once in `JIRA_WEEKLY_HOURS` who genuinely works only one board
  still gets an idle row - and that sprint's worth of available hours added
  to their total - for every *other* dated sprint present in the frame,
  even ones they hold no ticket on. There's no board-to-person roster
  anywhere in this codebase to correct this against, so it's left as-is and
  named as the function's second blind spot in its own docstring; the
  per-person `Sprints` column in the totals table is returned specifically
  so a reviewer can see which sprints actually contributed hours versus
  which just added idle capacity.

- **`capacity_table_by_sprint` groups by `sprint_name`, not `sprint_id`.**
  `sprint_id` is the more precise key (`render_shared._normalize_sprint_id`
  exists for exactly this reason), but that helper lives in a file this
  task does not own, and re-deriving its normalization logic here risked
  disagreeing with it. `sprint_name` is what the mockup and every existing
  per-sprint UI element in `render_shared.py` group and label by already
  (`_render_sprint_capacity`'s sprint picker, the ML-sprint detection at
  `render_shared.py:2385`), so this matches the existing convention rather
  than introducing a second, ID-based one that the page would then have to
  reconcile against. Named as a design choice, not a blind spot, because
  two differently-configured sprints sharing one name on one board would be
  a Jira data problem this shares with the rest of the dashboard, not one
  this function introduces.

## Render call sites for Phase 3

None of these are touched by this task (`app.py`, `render_shared.py`,
`pages/*.py` are out of scope). Listed for whichever task wires the UI:

- **`render_shared._render_hourly_capacity` (~`render_shared.py:3228`)** is
  the current single-sprint call site for `capacity.capacity_table` (via
  `capacity_table(committed, roster, start, end)` at `render_shared.py:3280`,
  called once per sprint the reviewer has selected in
  `_render_sprint_capacity`'s dropdown). This is the natural replacement
  point for `capacity.capacity_table_by_sprint(df, weekly_hours)` once
  Planning moves to the three-side-by-side-sprints layout `IMPLEMENTATION_PLAN.md`

  totals table becomes the new page-level "who's over/under, in total"
  view.

  the caller one level up (owns the sprint `st.selectbox` `IMPLEMENTATION_PLAN.md`
  3E replaces with three side-by-side cards); it is where
  `planning_metrics.carry_over_per_sprint`, `planning_metrics.no_priority_count`,
  `planning_metrics.outside_any_sprint_count`, and
  `planning_metrics.unestimated_per_sprint` have no call site yet and would
  be wired in alongside the capacity table.
- **`pages/planning.py`** (currently a 62-line stub forwarding to
  `render_shared._render_planning_page`, per `1C.md`'s frozen API list) is
  where `planning_metrics.ghost_assigned` has no call site at all today -
