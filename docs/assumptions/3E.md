# Task 3E assumptions — the Planning page

One bullet per ambiguous call, what was chosen, and why.

- **The "single sprint" ``st.selectbox`` and the ML-only ticket editor are
  two different tools, and only the first one was in scope to remove.**
  ``_render_sprint_capacity`` (877 lines, pre-3E) did two unrelated things
  behind one dropdown: pick a sprint to *summarise*, and — only when the
  picked sprint happened to be an ML-board one, Jira's own restriction —
  edit its tickets and write the result back to Jira (`Apply sprint
  selection`, add/remove from sprint, change status/priority/assignee/
  estimate). The task brief only asked to replace the summarising picker
  with three cards; deleting the writable editor as well would have removed
  real accountability tooling (exactly what the CEO/CTO brief asks for more
  of) that nothing in the acceptance criteria required gone. Kept it,
  unmodified in its own logic, and pointed it at the ML board's target
  sprint automatically instead of asking the reviewer to pick a sprint first
  — every other choice always produced the same "can't edit this one"
  warning anyway, so nothing the reviewer could actually *do* was removed.

- **One target sprint per board, ranked exactly the way the old dropdown's
  default (`index=0`) ranked the whole list.** Future before active before
  closed, earliest sprint name breaks a tie — applied per
  `sprint_board_id` group instead of once globally, so three boards produce
  three cards instead of one board "winning" the old dropdown's default.

- **A board's display name (`App`/`Marketplace`/`ML` in the mockup) comes
  from `teams.add_team()`'s existing team-resolution logic (assignee first,
  then `JIRA_TEAM_PROJECTS`), not a new board-id → name mapping.** There is
  no "board name" field in the Jira data this dashboard reads — only the
  numeric `sprint_board_id` and the sprint's own name (which is why
  `is_ml_sprint` already keyed off `sprint_name.startswith("ML Sprint")`
  before this task). Reusing `add_team` (already imported, already the
  codebase's one answer to "whose board is this") avoids inventing a second,
  competing way to name a board; a board with no resolvable team falls back
  to the literal `f"Board {id}"`.

- **The page-level dateless-sprint callout names every dateless sprint among
  the three cards, not only "the ML one."** The mockup and the task brief
  both talk about "the ML sprint" because that is the one real case today,
  but nothing in the compute layer (`planning_metrics`, `capacity.py`)
  assumes there is exactly one — if a second board's sprint ever loses its
  dates, the callout's title pluralises and lists all of them rather than
  silently reporting only the first.

- **The old per-sprint "Availability vs Commitment" table (fed by the live
  edits inside the ticket editor) is gone; the new cross-board capacity
  table (fed by the static committed frame, not pending edits) is the one
  canonical capacity view on the page.** These used to be two different
  numbers for the one editable sprint — old-table said what the *edited*
  frame would commit, everything else on the page said what Jira actually
  has now. Keeping both would mean deciding which one "the" capacity number
  is; the task's own framing ("capacity table with the Sprint column and
  cross-board sums") is unambiguous that the new page-level table is it. A
  reviewer mid-edit already sees a live "Pending row changes" preview table
  directly above the Apply button, so the tradeoff is not a silent one.

- **`_render_hourly_capacity`'s new signature is `(df)`, not `(sprint_df,
  in_sprint_df)`.** The old two-frame shape existed to separate "this
  sprint's window" from "tickets currently included in it" for one sprint's
  live edits. The new cross-board table has no single "current edit state"
  to read — it is `capacity.capacity_table_by_sprint(df, WEEKLY_HOURS)`
  applied once across every dated sprint in scope — so one frame in is the
  right shape. Its only caller is `_render_sprint_capacity`, in the same
  file, so this is not a break to any other page.

- **"Board hygiene" bars are computed org-wide (whatever `df` the whole page
  was called with), not scoped to the three cards' sprints.** The mockup's
  own subtitle says so directly ("all three boards") and the counts
  themselves (`no_priority_count`, `ghost_assigned`, orphan/empty epics,
  stuck-in-triage) are properties of the *board*, not of "the sprint
  currently showing" — narrowing them to the three target sprints would
  make "No priority: 3" read like a sprint-planning problem instead of the
  backlog-wide housekeeping gap it actually is.

- **"Unassigned" and "Outside any sprint" bars use two different existing
  compute paths on purpose, not the same one reused twice.** `Unassigned`
  is `assignee` blank/None over the whole `df` (mirrors the boolean test
  every other page's "no owner" tile already uses,
  `_NO_OWNER_NAMES`-based); `Outside any sprint` is
  `planning_metrics.outside_any_sprint_count`, which is specifically about
  `sprint_name` being blank. A ticket can be unassigned *and* in a sprint,
  or assigned *and* outside every sprint — conflating the two into one
  count would silently double-count neither and undercount both.

- **"Epics needing attention" / "Orphan tickets (no epic)" / "Empty epics"
  reuse `_render_epics`'/`_render_epic_organization`'s own compute calls
  verbatim (`epic_health_flags(epic_rollup(...))`,
  `epic_organization.suggest_parents`/`empty_epics`), not new functions.**
  These three numbers already exist on the Planning page (inside `_render_epics`,
  called earlier in `pages/planning.py`) with tiles reading almost the exact
  same English labels ("Epics needing attention", "Tickets with no epic
  (whole board)", "Epics with nothing open"). Recomputing them with the
  same calls, once more, for the hygiene bars keeps the two numbers
  identical by construction rather than risking a second, subtly different
  definition of "orphan" existing two sections apart on one page.

- **"Stuck in triage" is page-supplied when available, and falls back to an
  offline idle-days estimate only at the one call site that cannot supply
  it.** The real number (`fetch_triage_stuck_count`, JQL "in a triage status,
  created > Nh ago, no status change since") is a live Jira read
  `pages/planning.py` already pays for (via `_engineering_context()`'s
  bundle) to feed `_render_new_and_triage` a few sections above — threading
  it into `_render_sprint_capacity` as a new optional `triage_stuck_count`
  parameter costs nothing extra. `pages/engineering.py`'s call site (the
  legacy combined page, out of this task's file ownership) does not pass
  it, so that one bar falls back to `status in TRIAGE_STATUSES and idle_days
  * 24 >= TRIAGE_STUCK_HOURS` over the frame already in hand — an
  approximation of the same rule using `idle_days` instead of "no status
  change since," named as a fallback (`n/a`, dimmed bar) only when even
  `status`/`idle_days` are unavailable, never silently substituted for the
  real count without saying so.

- **Ghost-assigned's "genuine zero... with its evidence" is a footer
  sentence, not a per-bar link.** `theme_html.Bar` has no per-row link/note
  field (`name`, `value`, `pct`, `tone`, `dim`, `flag` only), so "evidence"
  here means: the zero case states in the card's footer that the check ran
  and found nothing ("no open ticket's assignee matches the departed-staff
  list"), and the nonzero case names up to five actual ticket keys in the
  same footer — the same "emit evidence, not a bare score" convention
  `planning_metrics.py` already documents for `GhostAssigned`, applied to
  where the page actually has room to show it.

- **The per-sprint "unknown is not low" table (`planning_metrics
  .unestimated_per_sprint`) is a second table under the capacity table, not
  a merged column of it.** `capacity.capacity_table_by_sprint`'s "Coverage"
  concept and `unestimated_per_sprint`'s "Coverage" concept are computed
  differently (hours-weighted committed/available vs. a raw estimated/total
  ticket ratio) and the acceptance bullet ("the unestimated cell renders
  `unknown`") is about the latter specifically. Keeping them as two tables
  means the `unknown` sentinel never has to survive being merged into a
  numeric `Utilization %` column that calls `pd.to_numeric` on its inputs —
  the exact collapse `planning_metrics.py`'s own docstring warns against.

- **`_render_sprint_capacity` and `_render_sprint_plan` are `@st.fragment`-
  decorated, which is why the new tests in `tests/test_planning_page.py`
  call `_render_sprint_capacity.__wrapped__(...)` instead of the function
  directly.** Calling a fragment-wrapped function outside a real Streamlit
  script run is not an error — it silently does nothing (no exception, no
  render call) — which would have made every assertion in this file
  trivially "pass" against a function that never ran. Streamlit's own
  `fragment()` decorator uses `functools.wraps`, so `.__wrapped__` reaches
  the real function; discovered this only after a first draft of these
  tests reported success while `theme_html.render` was never actually
  called — see the test module's own docstring.

- **`pages/planning.py`'s `_card()`/`_freshness_caption()` are duplicated
  from `pages/delivery.py`/`pages/today.py`, not imported.** Both are
  page-private helpers outside `render_shared`'s frozen API (1C.md), and
  both of the other pages already independently duplicate them rather than
  share a copy — matching that existing convention rather than introducing
  the first cross-page import of a private helper.
