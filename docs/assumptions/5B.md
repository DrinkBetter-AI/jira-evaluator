# Task 5B assumptions

One bullet per ambiguous call, what was chosen, and why - plus the parity
findings the task brief asked to have enumerated. This file also carries the
report-export gaps: they are findings a test proves, not a fix, since every
call site involved (`pages/code.py`, `pages/delivery.py`, `pages/people.py`,
`theme_html.py`, `render_shared.py`) sits outside this task's file
ownership.

## Harness shape

- **Extended, not duplicated.** `tests/apptests/_baseline_harness.py` /
  `baseline_apptest.py` already smoke-rendered six of the eight pages
  (Today, People, Delivery, Code, Planning, Engineering) against a
  synthetic 1000-ticket board with every optional integration switched off.
  Business and Integrity were added to the same `RENDERERS` dict and the
  same `PAGES` tuple rather than building a second harness, per the task
  brief's instruction to extend rather than invent.
- **Kept the embedded-string regeneration pattern - a first attempt to
  de-duplicate it was reverted.** Before this task, `baseline_apptest.py`
  carried `_baseline_harness.py`'s full source as an embedded triple-quoted
  string (`HARNESS_SOURCE`) and rewrote `_baseline_harness.py` from it on
  every run. A first pass here tried to remove that duplication - point
  `baseline_apptest.py` at the checked-in `_baseline_harness.py` directly
  (`AppTest.from_file(HARNESS)`) instead of regenerating it - reasoning
  that editing the harness in one place (to add Business/Integrity) was
  simpler than editing an embedded string. That is wrong for this repo
  specifically: `.gitignore` has `tests/apptests/_*_harness.py`, matching
  `_baseline_harness.py` and every sibling (`_ads_harness.py`, `_benchmark_
  harness.py`, `_burn_harness.py`, `_funnel_harness.py`) on purpose - they
  are generated build artifacts, and the embedded string in the tracked
  `*_apptest.py` file is the actual source of truth, regenerated fresh on
  every run so a stale or hand-edited copy on disk can never drift from
  it. Pointing `AppTest` at the file directly would have meant
  `_baseline_harness.py` is never committed and a fresh checkout (or CI)
  hits `FileNotFoundError` before a single page renders. Reverted:
  `baseline_apptest.py` still writes `_baseline_harness.py` from its own
  embedded `HARNESS_SOURCE` string on every run, now extended with
  Business/Integrity, matching every sibling harness's shape.
  `report_apptest.py`'s own harness-duplication (it `ast`-extracts
  `HARNESS_SOURCE` out of `ads_apptest.py`) is the same pattern and was
  left alone - it was not part of this task's file ownership and was not
  touched.
- **Integrity's non-admin session is the real gate, not a mock standing in
  for it.** The first attempt spied on `integrity.py`/`pr_quality.py`'s
  functions and expected to read a "zero calls" dict back from
  `st.session_state` after a non-admin run. That dict was never written:
  `access_gate.require_admin_password()` is not mocked for the default
  (non-admin) run, so its own real body runs - sees no
  `DASHBOARD_ADMIN_PASSWORD`, writes `st.error(...)`, and calls
  `st.stop()`. Under a real `AppTest` run (unlike a bare unit test, where
  `st.stop()` is a documented no-op - see `access_gate.require_admin_
  password`'s own docstring) that actually halts the script right there,
  before a single line after it executes. The harness now writes the
  spies' zero-initialised call-count dict to `st.session_state` *before*
  calling the page's render function, so what survives for a non-admin run
  is "every function, zero calls" - not because a spy reported zero, but
  because the live gate stopped the script before the spies' own
  post-render write could happen. This is a stronger proof than the
  mocked-gate version other tests in this repo use
  (`tests/test_integrity_page.py`): it exercises the actual, un-mocked
  `st.stop()` halting behaviour a live deployment relies on.
- **Admin session flips the gate by replacing the function, not by
  supplying a credential.** `BASELINE_ADMIN=1` makes the harness set
  `access_gate.require_admin_password = lambda: True`, the same technique
  `tests/test_integrity_page.py` already uses. No real
  `DASHBOARD_ADMIN_PASSWORD` is ever set - "no credentials of any kind
  present" (the task brief's phrasing) was read as covering the
  external-service credentials it names (Jira/GitHub/Slack/Fireflies/
  Clockify/DB), not the dashboard's own internal admin-session flag, which
  this harness never supplies a value for either.
- **The admin call-count assertion only requires the functions the page
  actually calls.** The admin-session proof asserts `cosmetic_touches`,
  `estimate_churn`, `reresolve_events`, `integrity_flags` and `pr_quality.
  self_merge` were each called at least once. `pr_quality.reciprocity` and
  `pr_quality.flag_self_merges` are spied (so the non-admin "zero calls"
  proof covers them too) but never asserted `>0` on the admin run:
  `pages/integrity.py`'s own body has no call site for either
  (`grep pr_quality\. pages/integrity.py` matches only the module
  docstring and this file's own comments) - only `pr_quality.self_merge`,
  from `_review_card`. Asserting `reciprocity`/`flag_self_merges` `>0` would
  have been asserting something the page was never written to do.
- **`test_report_parity.py` needed its own process-isolation fixture.**
  `AppTest.from_file(...).run()` executes a harness script in the *same*
  Python process, unlike the `*_apptest.py` scripts `tests/test_apptests.py`
  runs one subprocess per script for exactly this reason (see that module's
  docstring). The harnesses' module-level monkeypatches
  (`ads_client.load_ads_env = ...`, `github_client.load_github_env = ...`,
  `data_layer.fetch_tickets = ...`, `pages.code._engineering_context = ...`)
  are plain attribute assignments with no teardown; run in-process, they
  leaked past the test file and corrupted `tests/test_ads_client.py`,
  `tests/test_cost_client.py` and `tests/test_merchant_client.py` later in
  the same pytest session (all three call the real loader functions and got
  the stubs instead). Fixed with an autouse fixture in
  `test_report_parity.py` that registers each attribute with pytest's
  `monkeypatch` (`monkeypatch.setattr(obj, name, getattr(obj, name))` -  the
  standard "snapshot now, restore whatever it ends up as" trick) before any
  harness runs, so every test in that file leaves the shared module state
  exactly as it found it, regardless of what a harness script did to it in
  between. The same fixture also snapshots/restores `pio.templates.default`
  and whether `theme._TEMPLATE` is registered at all (`dashboard.inject_
  styles()` registers a "vinovoss" plotly template into that process-global
  registry and never unregisters it; left alone it turned `tests/test_
  price_charts.py::test_bigger_text_keeps_the_colours_the_app_already_drew_
  with` red the first time this file ran ahead of it - that test's own
  cleanup restores `pio.templates.default` to whatever string it captured
  at start, which is wrong if this file already left it pointed at a
  template object that test's cleanup then deletes; a latent assumption in
  a test file outside this task's ownership, worked around here rather
  than touched there), and calls `st.cache_data.clear()` before and after
  every test, since `data_layer.py`'s `@st.cache_data`-decorated fetch/
  derive functions share one process-wide cache outside a real Streamlit
  server session.
- **The real, hardest-to-find leak: `data_layer.py`'s on-disk board
  snapshot, not `st.cache_data`.** Even after the `pio.templates`/
  `st.cache_data.clear()` fixes above, `test_delivery_tiles_are_recorded_
  in_the_report` kept failing intermittently in a full, unfiltered `pytest
  -q` run - passing every time run alone or with the rest of this file,
  passing in both of CI's split invocations (`-m "not slow"`, `-m slow`)
  run separately, failing only in the single combined run the task's own
  baseline command uses. A first (wrong) theory was a collection-order
  interaction with `tests/apptests/test_changelog_fixture.py` (its mere
  presence in the same `pytest` invocation appeared to reproduce the
  failure reliably) - that did not hold up: isolating the same two files
  together repeatedly afterward passed every time, in both file orders,
  meaning the earlier "reproduction" was coincidental timing, not a real
  interaction between these two files. The real mechanism: `data_layer.
  _engineering_data()` persists its gathered board (df, `events`, PR data,
  the lot) to `_SNAPSHOT_PATH` - a fixed path under `tempfile.gettempdir()`
  (`/tmp/jira_dashboard_board_snapshot.pkl`), shared by every process on
  the machine, not scoped to a pytest session or even to this repo's own
  test runs. A fresh `AppTest` session always has empty `st.session_state`,
  so `_engineering_data()` always takes its "nothing held yet" branch and
  reads whatever bundle is sitting at that shared path - written by
  whichever engineering-page render (this file's own earlier tests,
  `tests/apptests/test_apptests.py`'s slow `baseline_apptest.py`
  subprocess, or any other process on the machine) happened to finish most
  recently - entirely bypassing this test's own stubbed `fetch_tickets`
  and its synthetic board. Confirmed directly: reading `test.session_
  state["tab_reports"]` on a failing run found a `Report` object present
  for the Engineering tab but empty (zero figures), and the rendered page
  showed `pages/delivery.py`'s "no changelog data read" fallback tiles
  (its `no_org_history` branch) rather than real numbers - the page ran
  correctly, against a bundle whose `events` genuinely was empty, because
  that bundle was not this test's. `st.cache_data.clear()` cannot fix
  this: the snapshot lives on disk, outside that registry. Fixed by
  calling `data_layer._delete_board_snapshot()` - the same helper the
  app's own "Refresh" affordance uses, whose docstring says exactly this:
  "a stale file cannot outlive the reads it came from" - both before and
  after every test in this file, so this file's tests always compute a
  fresh bundle from their own stub and never leave a snapshot behind for
  whatever runs next. `tests/test_board_snapshot.py` (a different file,
  outside this task's ownership) was checked and is not the source: it
  monkeypatches `data_layer._SNAPSHOT_PATH` to a temp-fixture path per
  test, so it never touches the real shared path. Verified with three
  consecutive full, unfiltered `python3 -m pytest -q` runs after this fix
  (1035 passed, 1 skipped, 6 xfailed each time) and both of CI's split
  invocations run separately immediately after.
- **`_code_report_data.py` is a new, narrow harness, not a reuse of
  `_baseline_harness.py` - and deliberately not named `_..._harness.py`.**
  Proving or disproving Code's report parity needs `github_ready=True`
  with a few realistic PRs; the credential-free baseline harness disables
  GitHub entirely, which proves the page degrades safely with nothing to
  show but never reaches `_render_code_kpis`/`_render_repo_coverage`/the
  stuck-queue table at all in that state (`_render_code_page` returns
  right after its "GitHub is unavailable" banner). The new harness
  monkeypatches `pages.code._engineering_context` directly - the same
  technique `tests/test_code_page.py`'s own "renders end to end with no
  GitHub data" case uses - rather than reaching for a real GitHub token.
  It is hand-authored and checked in directly (like `_synthetic_board.py`),
  not generated on every run the way `_baseline_harness.py` is, so it
  needed a name outside `.gitignore`'s `tests/apptests/_*_harness.py`
  pattern - `_code_report_harness.py` would have silently never been
  committed. Named `_code_report_data.py` instead.

## Changelog fixture

- **Hand-built, not generated - two tickets, seven changelog entries, saved
  as `tests/fixtures/changelog_snapshot.json`.** Every entry is one
  deliberate case, named in the JSON's own `_comment` key and again above
  each `EXPECTED_ROWS` entry in `tests/apptests/test_changelog_fixture.py`:
  a plain status transition with a named author (VV-100/h1), a label-only
  edit that is not a status move (VV-100/h2), a resolving transition
  (VV-100/h3, In Progress -> Review in Staging, both statuses chosen from
  `integrity.DEFAULT_RESOLVED_STATUSES`/its complement), the reopen straight
  back out of it (VV-100/h4), the re-resolution - a second, distinct entry
  into a resolved status on the same ticket (VV-100/h5), a second ticket's
  plain transition so its own resolution is not the ticket's first
  changelog entry (VV-200/h1), and a resolving transition with the
  `"author"` key removed from the history entry entirely - the
  deprovisioned-user / automation shape (VV-200/h2).
- **JSON, not a Python literal, is the fixture file.** `tests/fixtures/` is
  meant to hold data, not code; a `.json` file is also exactly the shape
  `JiraClient.search_issues(expand="changelog")` returns, so there is no
  translation step between "what Jira sends" and "what is pinned". The
  commentary that explains each entry lives in the test file next to the
  assertion it justifies (and once in the JSON's own `_comment` key, read by
  nobody but a human), rather than duplicated in both places where it could
  drift out of sync.
- **The pin is a hand-written `EXPECTED_ROWS` list, not a captured-then-
  frozen output of running the parser once.** Comparing against a computed-
  and-saved answer would only catch drift from *that* answer, which could be
  wrong from the start and would never be checked. `EXPECTED_ROWS` was
  written by reading `integrity.py`'s own field definitions
  (`changelog_events`'s docstring, `EVENT_COLUMNS`, `STATUS_STAGES`,
  `DEFAULT_RESOLVED_STATUSES`) and computing every field by hand, including
  `from_stage`/`to_stage` (`STATUS_STAGES["to do"]` etc.) and the "Unknown"/
  `None` author fallback.
- **Per-row parametrized tests, not one bulk `==`.** One
  `test_every_field_of_every_row_matches_the_pin` case per row (via
  `pytest.mark.parametrize`) means a failure names the row index directly
  in the test id, on top of the dict-equality diff pytest already prints
  per field - "this exact field, this exact row", the task brief's own
  phrasing.
- **The mutation proof flips one field a real attribution slip would flip.**
  `test_a_single_mutated_field_fails_exactly_one_row_comparison` changes
  VV-100/h1's `toString` from `"In Progress"` to `"In Review"` - a
  one-word difference, not a structural one - and asserts exactly row 0
  fails, on exactly `to_string` and `to_stage` (the second because
  `to_stage` is derived from `to_string` via `STATUS_STAGES`, so a real
  drift in one field's value legitimately moves both). Asserting "exactly
  these two fields, on exactly this one row" rather than "at least one
  field failed somewhere" is what proves the per-field comparison is
  actually independent per row, not a vague frame-shape diff that would
  fail everything or nothing.

## Report-export parity findings

Rendered end to end (real `AppTest` runs, real synthetic/stubbed data, not
static analysis) via `tests/apptests/test_report_parity.py` and
`tests/apptests/_code_report_harness.py`.

- **Confirmed working: Delivery's tiles.** `pages/delivery.py`'s single
  `theme_html.tiles([...], tab=TAB_ENGINEERING, section="Delivery")` call
  (the one call site Agent 1B's fix note explicitly names) does record -
  "Median In-Progress", "Staging round-trips", "Reopened · 30d" and
  "Unattributed" are all in the printable report, proven against the same
  synthetic board the render used.
- **Gap: Delivery's two `hbars()` calls carry no `tab=`/`section=`.**
  "Where open work sits, by team" and "Cycle time by status" both render on
  screen and are both absent from the report. Fix belongs to
  `pages/delivery.py` (a page module, outside this task's ownership) -
  pinned as `xfail(strict=True)` in `test_delivery_hbars_are_recorded_in_
  the_report`.
- **Gap: `theme_html.table()` has no `tab=`/`section=` parameters at all.**
  Unlike `tiles()`/`hbars()`, `table()`'s signature was never extended with
  a recording pair, so *no* call to it can ever record into the report,
  regardless of what the call site passes. This is the root cause behind
  every table-shaped gap below. Fix belongs to `theme_html.py`, outside
  this task's ownership - pinned as `xfail(strict=True)` in
  `test_delivery_stale_table_is_recorded_in_the_report` and
  `test_code_stuck_queue_table_is_recorded_in_the_report`.
- **Gap: Code's report is entirely empty.** With GitHub answering (proven
  via `_code_report_harness.py`, since the credential-free baseline harness
  never reaches these sections at all), `pages/code.py` renders its five
  headline PR tiles, "Review coverage by repo" bars and a stuck-PR table -
  and none of it is in the report. `_render_code_kpis()`'s
  `theme_html.tiles([...])` call and `_render_repo_coverage()`'s
  `theme_html.hbars(...)` call both carry no `tab=`/`section=`; the stuck-
  queue table is the `theme_html.table()` gap above. Fix belongs to
  `pages/code.py` - pinned as three separate `xfail(strict=True)` cases so
  a partial fix (e.g. tiles fixed, hbars not) still shows up precisely.
- **Gap: People's report is unconditionally empty; the "Download report"
  button never renders.** `pages/people.py` renders substantial content
  (18KB+ of markdown, a real `<table>`) but never calls `page_shared._tile`/
  `_kpis`/`_said`, and never calls `theme_html.tiles()`/`hbars()` at all -
  only the unrecordable `theme_html.table()`. `report.Report.empty` is true
  whenever a tab recorded zero figures and zero notes, and
  `page_shared._download_report` only draws the "Download report" button
  when `not built.empty` - so this is not merely "some content missing
  from the report", it is "no button, ever, on this page in its current
  state". Fix belongs to `pages/people.py` - pinned as
  `test_people_page_offers_a_download_report_button`
  (`xfail(strict=True)`).
- **Not a gap - a missing capability, and a design question:
  Today has no report at all.** `grep -n _download_report pages/today.py`
  matches nothing; the page never offers a "Download report" button
  regardless of what it draws (and its own `theme_html.tiles(tiles)`/
  `theme_html.hbars(bars)` calls carry no `tab=`/`section=` either, so even
  adding the button today would start from zero). Left out of
  `test_report_parity.py` entirely rather than pinned as an `xfail`,
  because the fix is not "pass `tab=`/`section=`" - it is "decide whether
  the landing page should have a printable report at all, and if so add
  the `_download_report(...)` call site" - a product decision for
  `pages/today.py`'s owner, not a parity bug this task can characterize
  with a single assertion.
- **Not clearly a gap - flagged as a decision point: Integrity has no
  report either.** Same `grep` result for `pages/integrity.py`. Given the
  page's own framing ("never a verdict", every card carries evidence
  precisely so a flag is checkable, not printable-and-forwardable out of
  context), the absence may well be deliberate - an admin-only page whose
  entire point is that its accusations stay inside the gated screen, not a
  PDF someone can forward. Recorded here as a question for whoever owns
  `pages/integrity.py`'s access model, not asserted as required.
- **Not investigated further: `render_shared.py`'s own bare `hbars()`/
  `table()` calls.** `render_shared.py` (which `pages/planning.py` and
  `pages/engineering.py` both draw through) has its own `theme_html.hbars(
  hygiene_bars)` call with no `tab=`/`section=`, and two more
  `theme_html.table(...)` calls - both a subset of the `table()` gap
  above. Planning's and Engineering's reports are *not* empty (both
  record real content through `page_shared._tile`/`_kpis` in other
  sections of the same file - 26 call sites across `render_shared.py`),
  so this is a partial-parity gap of the same shape as Delivery's, not a
  total one - but `render_shared.py` is out of this task's ownership and
  large enough (26 recording call sites, 3 non-recording ones found by
  inspection) that fully mapping every section's parity was left out of
  scope. Noted here rather than silently dropped.
- **Business has full parity in the credential-free harness - because it
  has nothing to report, not because it is broken.** Every source
  unconfigured means `pages/business.py` draws only "misconfigured"
  captions, so its report is empty - correctly. `pages/business.py` has
  zero bare `theme_html.tiles()`/`hbars()`/`table()` call sites at all
  (`grep` confirms); everything it draws goes through `page_shared._tile`/
  `_kpis`, which already record. `tests/apptests/report_apptest.py`
  (pre-existing, not modified by this task) already proves Business's
  report is populated correctly once real-shaped data answers - "Orders,
  Revenue & AOV", "Ads Spend & Return" and others are asserted there
  against a fully stubbed-but-populated Business page. Not re-tested here
  to avoid duplicating that harness's ~250 lines of stubbing for a case
  that already has coverage.

## CI

- **No new workflow needed.** `.github/workflows/checks.yml` already
  installs `requirements-dev.txt` and runs `python -m pytest -q -m "not
  slow"` then `python -m pytest -q -m slow` on every pull request and every
  push to `develop`/`main`, which is the full suite split by the same
  `slow` marker `pytest.ini` already declares - satisfying "CI runs the
  suite and fails the build on a red test" without a new file. Confirmed
  this task's new tests are picked up with no config change: `test_report_
  parity.py` and `test_changelog_fixture.py` are default-discoverable
  (`test_*.py`, no custom `testpaths` needed beyond the existing `tests
  optional`), and the extended `baseline_apptest.py` is already exercised
  through the existing `@pytest.mark.slow` parametrize in
  `tests/test_apptests.py` (`tests/apptests/*_apptest.py` glob).
