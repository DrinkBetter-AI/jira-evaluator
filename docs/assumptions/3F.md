# Task 3F assumptions

One bullet per ambiguous call, what was chosen, and why.

- **`ACTIVE_MERCHANTS` is semicolon-separated, not comma-separated.** The
  pre-existing code in `pages/business.py` split on `,`, but
  `roles_template.env`'s own `ACTIVE_MERCHANTS` line (and every other
  variable in that file - `JIRA_ROLES`, `GITHUB_LOGIN_MAP`, ...) is
  semicolon-separated, because a merchant's catalogue name is free to carry
  a comma of its own ("Little International Wine, Inc" is one shop, not
  two). The old comma split was a latent bug: pasting the real
  `roles_template.env` value into Cloud Run's env would have produced one
  merchant name equal to the whole string. Fixed to split on `;`, matching
  the file that is now the source of truth.

- **The five-merchant default is baked into `pages/business.py` verbatim**,
  copied from `roles_template.env`'s `ACTIVE_MERCHANTS` line, following the
  exact pattern `roles.py` already uses for `JIRA_ROLES` et al. (baked
  constant, not a runtime read of the `.env` file, so a missing or stale
  file on a deploy target can't blank out the roster). The env var wins when
  set; unset - which is Cloud Run's actual state today - the page now
  filters by this list instead of by nothing. Little International is not
  in it, in either path, per `DEVIN_PLAN`'s own resolution: the vendor panel
  screenshot is newer than `DEVIN_PLAN` prereq 3 and wins.

- **The store-metadata key question lives in `merchant_client.py` as a pure
  function, not as a SQL-issuing one.** `merchant_client.py`'s own docstring
  says it speaks HTTP, not SQL, "like its neighbours" (`orders_client.py`
  owns the medusa connection); `orders_client.py` is out of scope for this
  task ("any other compute module"). So `merchant_client.resolve_store_status`
  takes an already-fetched `(metadata_dict, store_name)` and returns
  `(active, matched_key)` - it never opens a connection. The actual
  best-effort live read (`select name, metadata from medusa.store limit
  12`) is issued from `pages/business.py` (`_store_metadata_note_cached`),
  using `orders_client.load_medusa_env()` for credentials and `psycopg2`
  directly, the same way `_offer_merchants_cached` already reaches the same
  database - without adding a query to `orders_client.py` itself. It is
  read-only, cached for an hour, and every failure path (no DB configured,
  connection refused, bad credential) degrades to a caption saying so rather
  than raising. **Verification step for the next person with DB access**,
  exactly as `DEVIN_PLAN` 0.6 and `HANDOFF.md` describe it:

  ```sql
  select name, metadata from medusa.store limit 12
  ```

  Read the `metadata` column for each row and see which of `status`,
  `store_status`, `is_active`, `active` is actually present and meaningful.
  If every row agrees on one key, `merchant_client.STORE_STATUS_KEYS` can be
  trimmed to that one entry - the page's own caption (`_store_metadata_note`)
  says this in one line once it can reach the database, e.g. "Safe to trim
  merchant_client.STORE_STATUS_KEYS to just that one."

- **A present-but-unrecognised metadata value stops the chain rather than
  falling through to the next key.** `resolve_store_status` finds `status`
  present with value `"pending-review"` and returns `(None, "status")`, not
  a fallthrough to `store_status`. Falling through would silently prefer
  whichever key happens to parse over the key the store is actually using -
  the chain is meant to be explicit and ordered, not "first key that makes
  sense to this function".

- **The two remaining pies became hand-rolled ranked bars, not
  `theme.rank_bar`.** `theme.rank_bar` exists and is used elsewhere for
  exactly this pie-to-bar conversion, but it draws every named row in one
  colour (it exists for "who is on top, by how much" rankings with no
  colour of their own). Both pies here carry deliberate, meaningful colour -
  green/red price bands (`merchant_letter.BAND_COLOURS`), sold/not-sold ad
  spend (`ads_evidence.SPLIT_COLOURS`) - which is the whole point of the
  section's own docstring ("this much of what Google could compare is red,
  and the red is the part that is not selling"). Losing that to a uniform
  bar would have been a worse chart for a merchant-facing report. Built
  instead as a sorted, labelled `px.bar` keeping the same
  `color_discrete_map`, ordered ascending (smallest first) so the largest
  value - the one to act on - lands at the top of the plotted stack, the
  same visual convention `rank_bar` uses. Both are still zero `px.pie`/
  `go.Pie` traces, and text-labelled with the value on each bar, so the
  underlying acceptance criterion ("ranked bar, not a pie") is met either
  way.

- **`theme.apply_palette()` added explicitly to the two single-series bars
  that had no colour of their own** (orders-per-day, funnel steps) so their
  colour traces to `theme_tokens.colorway()` rather than to whatever
  Streamlit's own default Plotly template happens to supply -
  `theme.chart_fonts()` only copies the *font* size onto the active
  template, not a colourway, so an unstyled `px.bar` was drawing outside the
  token system. The charts with their own deliberate `color_discrete_map`
  (the two ranked bars above, and the price-ladder/scatter charts) were left
  alone: their colour already comes from a value, not a default, and is
  meaningful rather than arbitrary.

- **`#6b7280` (the "market" reference marker/vline colour, used twice) has
  no exact match in `theme_tokens`.** Substituted `theme_tokens.INK["3"]`
  (`#64748b`) - the closest neutral, muted tone in the ladder, used
  elsewhere for secondary/tertiary text. The other four literal hexes in
  `pages/business.py` matched a token exactly: `#111827` → `INK["1"]`,
  `#b91c1c` → `STATUS["crit"][0]`, `#15803d` → `STATUS["good"][0]`,
  `#1d4ed8` → `STATUS["info"][0]`.

- **Vivino-blocked detection is a substring check on the exception's
  string form (`"403" in str(exc)`), not a status-code attribute.**
  `vivino_client.py` always wraps a 403 into a `VivinoError` (or lets a bare
  `requests.HTTPError` through) whose message text carries "403" - by the
  time it reaches `pages/business.py` there is no `.status_code` left to
  read. A string check is cruder than an attribute check but is the
  information that is actually available at the catch site, and a miss
  (timeout, 5xx, a changed page) still falls through to the pre-existing
  generic warning unchanged.

- **`tests/apptests/benchmark_apptest.py`'s pre-existing fixtures were
  renamed to stop colliding with the now-live `ACTIVE_MERCHANTS` default.**
  Two fixture shop names - `"Little International Wine, Inc"` (there
  specifically to test a comma inside a name) and `"Blackbear"` (there to
  test one wine stocked by two shops) - happened to match or nearly match
  real merchant names the new default excludes or doesn't recognise, and
  the fixtures predate this task, so they were testing something unrelated
  to active/inactive filtering. Renamed to `"Two Rivers Wine, Inc"` and
  `"Rivermont"`, which exercise the same edge cases without being read as a
  live policy decision. The harness also now sets `ACTIVE_MERCHANTS`
  explicitly to a roster covering every shop name its own fixtures use
  (`Yiannis;Rivermont;Two Rivers Wine, Inc;Yiannis Wine Shop`), so this
  smoke test keeps validating "every merchant" rendering behaviour
  independent of whatever the production default happens to be - that
  default has its own, separate coverage in `tests/test_price_charts.py`.
  Regenerating `_benchmark_harness.py` (the checked-in copy `run()` writes
  fresh each call) picks up both changes automatically; it was left as
  `benchmark_apptest.py` regenerated it, not hand-edited.

- **A new `vivinoblocked` mode was added to the same harness** rather than a
  separate, smaller AppTest script, since it needed the same merchant-picker
  and button-gate scaffolding the existing `vivino` mode already builds -
  duplicating that scaffolding elsewhere would have been the same fixture
  twice. `texts()` (the harness's own "everything the page said" helper) was
  extended to also collect `st.info` output, which it did not before; this
  is additive to every existing scenario's assertions, none of which check
  for the *absence* of specific text that would collide.
