# Task 2C assumptions — roles and rubrics (WP5)

One bullet per ambiguous call, what was chosen, and why.

- **`roles_template.env`'s 16-key list is the authoritative source, not
  `ROSTER.md`'s own "paste-ready" env block.** `ROSTER.md`'s "Env values
  (paste-ready)" section (lines ~66-68) carries an *older*, 11-chip
  `JIRA_ROLES` string (`ml`, `mobile`, `marketplace`, `design`, `qa`,
  `frontend`, `backend`, `pm`, `infra`, `seo`, `exec`) that the same document
  explicitly describes as what the 16-key taxonomy "collapses into" for the
  People-page UI. The task brief names the 16 keys directly and frames
  `roles_template.env` as "current as of today and authoritative," and that
  file's own header confirms it was regenerated 19 Aug with exactly those 16
  keys. Built the roster and rubric table against the 16-key set. The
  11-chip UI grouping in `ROSTER.md` is a separate, later concern (how the
  People page's filter chips group roles for display) that this task does
  not implement - `roles.py` exposes `ROLE_LABELS` and `CODE_ROLES` etc. so a
  UI layer can build that grouping on top without needing its own copy of
  the roster.

- **"biz-dev" in the task brief is not a 17th role key.** The task text says
  "SEO, wine, advisor and biz-dev have no rubric," but `biz-dev`/`bizdev` is
  not one of the 16 keys - `roles_template.env`'s own header names `bizdev`
  as exactly the kind of stale, invalid key this task exists to stop rubric
  lookup from keying off. `ROSTER.md` explains the mismatch: Praveen Rai
  does biz dev, but his role key is `exec` (`"Praveen Rai | exec (biz dev)"`
  in the roster table), and exec is never scored regardless. Read "biz-dev"
  in the task brief as describing Praveen's job function, not a role key to
  add. No `biz-dev` role or rubric exists in `roles.py`; `NO_RUBRIC_ROLES ==
  {"seo", "wine", "advisor"}` (asserted by a test), and Praveen falls under
  the `exec` sentinel.

- **Roster name lookups are case-insensitive.** `roles_template.env`'s
  comment says role assignment names "must match Jira assignee display
  names exactly (matched case-sensitively)" - but that instruction is about
  matching the roster against live Jira ticket/PR data, a concern that
  belongs to whichever module joins this roster against ticket frames (out
  of this task's scope: `roles.py` never touches a ticket dataframe).
  Within `roles.py` itself, every lookup (`person`, `role_of`, `login_for`,
  `is_active`) keys on `name.strip().lower()` for a more usable API and to
  avoid a lookup silently missing "tam" vs "Tam". A later integration point
  that joins the roster against Jira assignee strings should preserve exact
  casing from `Person.name` when it matters.

- **Former-staff entries win over a same-name active entry.** No overlap
  exists in the current default data, but `load_roster` applies
  `JIRA_FORMER_STAFF` after `JIRA_ROLES`, so if a name were ever listed in
  both, the departed flag wins: `active=False, role=None`. A departed
  person should never end up scored because a role assignment lingered.

- **`roles.MIN_PEERS` is a new, independent constant, not imported from
  `kpi.MIN_PEERS`.** Both equal 3 today but gate different questions -
  `kpi.MIN_PEERS` gates the code rubric's ticket-count peer percentile,
  `roles.MIN_PEERS` gates role-cohort membership for peer comparison in
  general. Keeping them separate means `roles.py` has no import-time
  dependency on `kpi.py` (only the reverse, which the task requires for
  rubric selection), so there is no import cycle. `tests/test_roles.py`
  does not assert the two stay equal; if a future PM decision diverges them,
  nothing here forces them back together.

- **`roles.CODE_RUBRIC`'s nine components are a hand-kept copy of
  `kpi.WEIGHTS`, not an import of it.** `kpi.py` now imports `roles.py` (for
  `kpi.rubric_for`), so `roles.py` importing `kpi.py` back would cycle.
  Copied the nine names/weights literally into `roles.CODE_RUBRIC` instead,
  and added `tests/test_roles.py::test_code_rubric_weights_match_kpi_weights_exactly`
  (asserts `roles.CODE_RUBRIC.weights() == kpi.WEIGHTS` and the totals
  match) so the two copies cannot silently drift apart - if either changes
  without the other, the test catches it immediately rather than the
  rubric and the actual scoring code quietly disagreeing.

- **Five new rubrics (QA-automated, QA-manual, PM, designer,
  infrastructure) have no prior art anywhere in this codebase** - grepped
  for "rubric" and every WP5-adjacent phrase from `ROSTER.md`
  (board hygiene, triage latency, bug validity, verified, estimate
  coverage) and found nothing beyond the code rubric already in `kpi.py`.
  Designed all five component tables from scratch, following
  `KPI_SPEC.md` §1's four rules directly: weights sum to a documented total
  (enforced at construction, see below), every component names a blind
  spot in a required `Weight.blind_spot` field, and the two components
  `ROSTER.md` explicitly calls for (designer leaning on cycle time /
  estimate accuracy over PR volume; infrastructure leaning on estimate
  accuracy and hours-vs-delivery as "exactly the padding checks") are built
  to reference the specific `KPI_SPEC.md` §3 metrics that already exist
  (`estimate_accuracy.py`, `integrity.py`) for exactly that reason. None of
  these five rubrics has a component-computation function behind it yet
  (i.e., nothing in this task computes "Triage latency" from real ticket
  data) - that's future work; `roles.overall()` is the generic scoring
  engine later agents call once each rubric's inputs are built, mirroring
  `kpi.overall()`'s "insufficient data, never a flattering fragment" shape.

- **"Does not round" is enforced as a hard raise at `Rubric.__post_init__`,
  with `1e-9` float tolerance** (for ordinary floating-point summation
  noise, not as slack for an actually-wrong table). A rubric whose weights
  sum to anything else raises `ValueError` on construction, so a bad table
  fails at import time, not at scoring time on someone's actual page.
  `Weight.__post_init__` separately rejects a blank blind spot and a
  non-positive weight, for the same "fail at construction" reason.

- **`roles.overall()`'s "insufficient weight" threshold is 60% of the
  rubric's own total**, mirroring `kpi.MIN_SCORABLE_WEIGHT` (60 of 100)
  exactly but expressed as `MIN_SCORABLE_FRACTION = 0.6` against
  `rubric.total` so it generalizes to any future rubric whose total isn't
  100 (none currently isn't, but nothing in `Rubric` requires 100).

- **`rubric_for_role`'s `"unclassified"` status is deliberately
  unreachable today** - the module-level assertion right after
  `ROLE_RUBRIC` is built checks that `ROLE_RUBRIC.keys() | NO_RUBRIC_ROLES |
  {"exec"}` exactly equals `set(ROLE_ORDER)`, and raises `AssertionError` at
  import time if not. `"unclassified"` exists as the *value*
  `rubric_for_role` would return for a role string outside that union, so
  that `tests/test_roles.py`'s "every key parsed from `JIRA_ROLES` resolves
  to `scored`/`no_rubric`/`exec`, never `unclassified` or `role_unknown`"
  assertion is a real, meaningful check (parametrized at collection time
  over `roles.load_roster().roles()`, not over a static list) rather than
  one that could never fail. Between the import-time assertion and the
  collection-time parametrization, a role added to `JIRA_ROLES` without a
  rubric decision fails the test suite in two independent places before it
  could ever reach a silently-dropped role in production - the exact bug
  this task exists to close.

## Public API of `roles.py` (for later agents to code against)

**Roster**
- `Person(name: str, role: str | None, active: bool, github_login: str | None = None)` — `.key` (lowercased identity)
- `Roster(people: dict[str, Person], unmapped_logins: tuple[str, ...], login_index: dict[str, str])`
  - `.person(name) -> Person | None`
  - `.role_of(name) -> str | None`
  - `.is_active(name) -> bool | None`
  - `.login_for(name) -> str | None`
  - `.name_for_login(login) -> str | None`
  - `.roles() -> tuple[str, ...]` (distinct role keys present, sorted)
  - `.people_in_role(role, active_only=True) -> tuple[Person, ...]`
- `load_roster(env: Mapping[str, str] | None = None) -> Roster` — env overrides the baked `roles_template.env` defaults, per-variable

**Rubrics**
- `Weight(name: str, points: float, blind_spot: str)` — raises on blank name, non-positive points, or blank blind spot
- `Rubric(rubric_id: str, label: str, components: tuple[Weight, ...], total: float = 100.0)` — raises if weights don't sum to `total`; `.weights() -> dict[str, float]`
- `CODE_RUBRIC`, `QA_AUTOMATED_RUBRIC`, `QA_MANUAL_RUBRIC`, `PM_RUBRIC`, `DESIGNER_RUBRIC`, `INFRASTRUCTURE_RUBRIC`
- `ROLE_RUBRIC: dict[str, Rubric]` — every scored role key -> its `Rubric`
- `NO_RUBRIC_ROLES: frozenset[str]` — `{"seo", "wine", "advisor"}`
- `CODE_ROLES: frozenset[str]` — the 7 role keys sharing `CODE_RUBRIC`
- `ROLE_ORDER: tuple[str, ...]`, `ROLE_LABELS: dict[str, str]` — the 16 keys and their display labels
- `EXEC_ROLE = "exec"`, `EXEC_REASON = "exec — not scored"`
- `RubricLookup(role, status, rubric, reason)` — `status` in `{"scored", "no_rubric", "exec", "role_unknown", "unclassified"}`
- `rubric_for_role(role: str | None) -> RubricLookup`
- `rubric_for_person(roster: Roster, person: str) -> RubricLookup`

**Scoring**
- `OverallResult(score: float | None, reason: str)`
- `overall(person: str, roster: Roster | None = None, component_scores: Mapping[str, float] | None = None) -> OverallResult`
- `MIN_SCORABLE_FRACTION = 0.6`

**Cohorts**
- `MIN_PEERS = 3`
- `cohort_key(role: str | None) -> str | None` — folds `frontend`/`frontend-mobile`/`mobile` into one id; everything else maps to itself
- `CohortResult(person, role, cohort, peers, peer_count, sufficient, reason)`
- `peer_cohort(roster: Roster, person: str) -> CohortResult`

**`kpi.py` addition (additive only, existing names untouched)**
- `kpi.rubric_for(person: str, roster: roles.Roster | None = None) -> roles.RubricLookup` — thin delegate to `roles.rubric_for_person`
